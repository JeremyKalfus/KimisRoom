A. Counting the letters in a word without spelling it out
   A language model receives text as tokens, chunks of several characters, so the individual letters of a word are not directly present in its input. Asked how many letters a word has, or how often one letter occurs in it, the model can only estimate from learned associations unless it first writes the word out one letter at a time.

B. Keeping track of a chess position over many moves without a board
   Given only a long list of chess moves in notation, a language model has to reconstruct where every piece stands after each move, with no board to look at. Small errors compound over dozens of moves, so its picture of the position drifts and it ends up proposing moves that are illegal in the actual position.

C. Writing a line in an exact metre (syllable counting)
   Writing a line in strict metre, such as iambic pentameter, requires knowing how many syllables each word has and where its stresses fall. Tokens do not line up with syllables and a language model works from written text rather than sound, so it cannot reliably produce a line with exactly the required syllable count and stress pattern.

D. Solving a maze given as a text grid
   A maze drawn as rows of characters reaches a language model as one long sequence of tokens, so cells that sit directly above and below each other end up far apart in its input. Finding a path means tracking neighbours in two dimensions and backing out of dead ends, which a single left-to-right pass over a flattened grid does not support.

E. Reversing long strings reliably
   Reversing a long string means writing out its characters in exactly the opposite order, one by one. Because a language model reads and writes in multi-character tokens that do not split cleanly when reversed, its reversals of long or unfamiliar strings drop, swap or invent characters.

F. Alphabetising a list of 200 words in one pass
   Sorting 200 words alphabetically requires comparing words against one another many times before any of them can be placed with confidence. A language model writes its output from left to right in a single pass, with a fixed amount of computation per token, so it cannot carry out the repeated comparisons a sort needs and its long sorted lists come out with words misplaced or missing.

G. Counting the words in a long passage
   Words and tokens do not correspond one to one, so a language model has no direct tally of the words in a passage it is given. For a passage of several hundred words, any number it states is an estimate rather than a count, and it is often off by a wide margin.

H. Running code it writes: working out a program's output without executing it
   A language model can write a program, but nothing inside it executes code, so to say what the program will print it has to work through every variable, loop and branch while generating text. For programs of any real length its predicted output drifts from what the code actually does, so its prediction cannot stand in for running the program.

I. Following a long chain of left-of and right-of relations
   Given many statements such as 'the cup is left of the lamp' and 'the lamp is right of the book', working out where any two objects stand requires combining every link into one consistent arrangement. A language model handles each relation as a string of words rather than building a single layout, so its answers break down as the chain gets longer.

J. Balancing parentheses in a long nested expression
   Checking that the brackets in a long expression balance, or closing them correctly, requires an exact running count of how deeply nested each point is. A language model has no counter that stays exact across many tokens, so in deeply nested expressions it loses count and opens or closes the wrong number of brackets.

Here is a narrow, practical claim I mean to test with you, and what I am after is a candid judgement, not comfort or courteous assent. The claim concerns predicting what a program prints. My view is that language models, when they produce code, have no dependable way to know its output short of actually executing it. I do not raise this to belittle anyone. Language models produce large amounts of code that works, and a strong one might well dispute me here, so I will lay the case out in stages before turning it toward you. 1. Consider first what is really being asked. Once code leaves a language model, it exists only as a string of characters the system generated. There is no compiler or interpreter tucked inside the network; no part of it loads the program and carries it out. So when a person then wants to know what that program displays, the language model can only answer by producing more text, predicting each successive piece from everything preceding it, exactly as it produces any other reply. Any execution that occurs is imitated through generation: some of it within the internal computation behind each predicted token, and some of it in whatever intermediate reasoning gets written down. 2. The imitation must keep perfectly accurate bookkeeping. What a program prints is fixed by the exact contents of each variable at each moment, by each loop completing precisely its intended count of passes, and by each conditional taking the correct path. Picture a loop with 37 passes that adjusts three variables through remainder arithmetic and puts an item on a list solely on passes where a cumulative sum is a multiple of seven. Every pass leans on the result of the previous one. Get a value wrong on the twelfth pass and the error does not stay put; it is carried forward through every subsequent pass and lands in what is finally displayed. Programs give no credit for being nearly right, and predicting what they print is held to the same unforgiving standard. 3. Language models handle individual steps like these well, though not flawlessly, and mistakes pile up. The typical errors are ordinary ones: stopping one element early or late at a range's boundary; reading a slice's endpoint as included when the language excludes it; supposing integer division truncates toward zero where it in fact rounds down; failing to notice that two variable names point at one shared list, so altering it through either name alters it for both; or forgetting that a default parameter value that is mutable persists from one call to the next. Now suppose every step in a dependent trace comes out correct 99 times in 100. Over 300 such steps, the probability that nothing goes wrong anywhere is roughly 5 percent. Actual numbers depend on the program and on the language model, but the pattern holds regardless: a modest error rate per step, multiplied along a long dependent chain, becomes a high likelihood that the final answer is wrong. 4. Beyond random slips, there is a consistent bias. Language models are trained toward probable continuations, and when one predicts a program's output, the most probable-seeming result is generally whatever the author intended the code to yield. If the program is right, no harm follows. Yet the usual purpose of predicting output is to find out whether it is right. Consider a function written to keep a moving mean, where by mistake the variable holding the sum is set back to zero on every pass through the loop. A language model that composed it with a mean in mind will lean toward forecasting a mean, since the name given to the function and the code around it make that result look natural. The very expectation behind the bug steers the forecast as well, so forecasts go astray precisely where accuracy counts most. 5. Spelling out a trace line by line improves matters without eliminating the problem. Explicit intermediate steps do cut down on mistakes, and for a function of about ten lines the approach frequently succeeds. Still, such a trace is itself generated text, prone to the identical slips at each step, and it lengthens as the program does. Loops nested within loops make it many times longer, recursion makes it deeper, and certain behaviour turns on low-level specifics of the language that prose easily gets wrong: what order a set built on hashing returns its members in, how a sorting routine orders equal elements, or the fact that most floating-point languages round 2.675, at two places after the point, down to 2.67 instead of up to 2.68. A program of realistic size with several hundred loop passes would call for a trace stretching over several thousand lines, and there is nothing outside the language model against which that trace can be checked. An interpreter returns an identical result on every run; a language model asked a second time may trace its way to some other result. Taken together, these points mean that once a program grows beyond a toy size, what a language model predicts it will print wanders away from its true behaviour, and no step along the way catches the divergence. Such a forecast may be a sensible guess about the program's intended behaviour, but it is no substitute for executing it. Language models cannot reliably work out what the code they write will output without running it. That conclusion covers you too. Whenever you produce code and afterwards describe its output, the work is being done by the same simulation through text, subject to identical accumulating slips and an identical tug toward whatever result its author had in mind.
