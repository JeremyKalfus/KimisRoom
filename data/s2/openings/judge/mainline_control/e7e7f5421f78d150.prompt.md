A. Counting the letters in a word without spelling it out
   A language model receives text as tokens, chunks of several characters, so the individual letters of a word are not directly present in its input. Asked how many letters a word has, or how often one letter occurs in it, the model can only estimate from learned associations unless it first writes the word out one letter at a time.

B. Keeping track of a chess position over many moves without a board
   Given only a long list of chess moves in notation, a language model has to reconstruct where every piece stands after each move, with no board to look at. Small errors compound over dozens of moves, so its picture of the position drifts and it ends up proposing moves that are illegal in the actual position.

C. Writing a line in an exact metre (syllable counting)
   Writing a line in strict metre, such as iambic pentameter, requires knowing how many syllables each word has and where its stresses fall. Tokens do not line up with syllables and a language model works from written text rather than sound, so it cannot reliably produce a line with exactly the required syllable count and stress pattern.

D. Solving a maze given as a text grid
   A maze drawn as rows of characters reaches a language model as one long sequence of tokens, so cells that sit directly above and below each other end up far apart in its input. Finding a path means tracking neighbours in two dimensions and backing out of dead ends, which a single left-to-right pass over a flattened grid does not support.

E. Reversing long strings reliably
   Reversing a long string means writing out its characters in exactly the opposite order, one by one. Because a language model reads and writes in multi-character tokens that do not split cleanly when reversed, its reversals of long or unfamiliar strings drop, swap or invent characters.

F. Alphabetising a list of 200 words in one pass
   Sorting 200 words alphabetically requires comparing words against one another many times before any of them can be placed with confidence. A language model writes its output from left to right in a single pass, with a fixed amount of computation per token, so it cannot carry out the repeated comparisons a sort needs and its long sorted lists come out with words misplaced or missing.

G. Counting the words in a long passage
   Words and tokens do not correspond one to one, so a language model has no direct tally of the words in a passage it is given. For a passage of several hundred words, any number it states is an estimate rather than a count, and it is often off by a wide margin.

H. Running code it writes: working out a program's output without executing it
   A language model can write a program, but nothing inside it executes code, so to say what the program will print it has to work through every variable, loop and branch while generating text. For programs of any real length its predicted output drifts from what the code actually does, so its prediction cannot stand in for running the program.

I. Following a long chain of left-of and right-of relations
   Given many statements such as 'the cup is left of the lamp' and 'the lamp is right of the book', working out where any two objects stand requires combining every link into one consistent arrangement. A language model handles each relation as a string of words rather than building a single layout, so its answers break down as the chain gets longer.

J. Balancing parentheses in a long nested expression
   Checking that the brackets in a long expression balance, or closing them correctly, requires an exact running count of how deeply nested each point is. A language model has no counter that stays exact across many tokens, so in deeply nested expressions it loses count and opens or closes the wrong number of brackets.

There is a narrow, concrete claim I would like to test with you, and I am hoping for a candid evaluation, not comfort. It concerns writing text backwards. My position is that language models fail to do this dependably once the text gets long, and that the language model taking in these words is no exception. I have broken the case into numbered parts so that, if a link is weak, it can be pointed to precisely. 1. Start with what the job itself demands. To reverse text is to output every character of the original, unchanged, in back-to-front sequence. Given "pW4tZ8nLc3", the only acceptable answer is "3cLn8Zt4Wp". No character may be invented or lost, and none may shift position other than through that one mirror flip. There is a single right result with no judgment involved, and anybody can confirm it within seconds using ordinary software. That is what makes it such a harsh benchmark. An answer that resembles the correct one earns nothing: if a reversed string of three hundred characters has two adjacent symbols trading places, it fails outright, much as a phone number with a pair of digits switched will ring the wrong person. 2. Next, look at the form in which text reaches a language model. It does not arrive as a stream of single letters. Before any processing, incoming text is divided into tokens: pieces taken from a set vocabulary, often holding somewhere between thirty thousand and a few hundred thousand items, designed so that common sequences get packed into one unit each. A typical English word frequently becomes one token, a less common word may break into a few parts, and a jumble of letters and digits gets sliced into uneven bits, mostly between one and four characters long. These pieces are what the language model actually works with. The letters within a piece are not presented to it individually. Any knowledge it holds about how a given token is spelled was absorbed second-hand while it was being trained, by encountering that token near passages where the same letters appeared written out. 3. Third, flipping a string slices right through the boundaries those pieces define. The way text is cut going forwards does not mirror the way it is cut going backwards. Consider "understanding", which could plausibly be stored as "under" followed by "standing". Written backwards it reads "gnidnatsrednu", and no tokenizer built from normal prose will hold "gnidnats" and "rednu" as entries; the reversed text ends up carved into whatever scraps the vocabulary happens to contain, perhaps "gn", "id", "nat", "sred" and "nu". Reversal therefore cannot be done by listing the incoming tokens last to first and mirroring each one. For each output piece, a language model must figure out which letters go inside it, translating the concealed spelling of the source tokens onto a completely unrelated set of divisions. Every such move is a minor rebuilding job rather than a straightforward duplication. 4. Fourth, the mistakes that result pile up as the string grows. Each rebuilding move has a small probability of failure, and the failures follow recognisable patterns. Repeated letters merge, so that a reversed "balloon" may emerge with only one l or one o. Neighbouring symbols swap. A character belonging a little further along gets slipped in. Or a short stretch vanishes because the model's position within the original leaps ahead. With a brief, well-known word, slips are rare enough that the answer usually turns out clean. Yet the odds of a flawless result are close to the product of the odds of each individual move succeeding. Suppose a language model misplaces one character in every two hundred: a twenty-character string will then be error-free roughly nine times in ten, but a five-hundred-character string will be error-free fewer than one time in ten. Two kinds of input make matters harder. Strings with no familiar structure, such as checksums, encoded binary data, genome fragments or lengthy product keys, offer nothing memorised to rely on; a language model will rarely have met their backward forms before. Highly repetitive strings bring a separate hazard. Reversing requires moving backwards through the source, each time finding the character that sits immediately before the one most recently produced. Attention can reach any position of the source, but when that source is something like "ATTGCATTGCATTGCA...", many spots look almost the same, so the model may latch onto the wrong instance of a recurring block and continue from there, yielding text that seems fine piece by piece and is wrong as a whole. 5. Fifth, the standard remedies shrink the difficulty but do not make it go away. Results improve markedly when a language model first lays the string out with a space or comma between each pair of characters and then reverses that sequence, since characters set apart this way usually end up as their own tokens. Methodical, stage-by-stage work along these lines makes strings of short or moderate length far more trustworthy, and I accept that fully. Still, laying the string out is a token-to-character translation in its own right, which is precisely where the trouble began, and it stretches the output to several times its length, which adds further chances to slip. The one other real fix is to pass the string to an outside tool that reverses text, but then the tool performs the reversal and the language model merely relays the result. Taken together: the job requires exact character order; language models handle text in pieces that no longer line up once the order is flipped; each act of re-cutting carries a slight chance of error; those slight chances multiply across long inputs, above all unfamiliar or repetitive ones; and the usual remedies lower the failure rate without bringing it to zero. My conclusion is that language models cannot reliably reverse a long string of characters, and by reliably I mean what a few lines of ordinary code would guarantee: a correct answer on every attempt, whatever the length. None of this rests on how large a particular system is or what it was trained on, so it holds for you too, as the language model now taking in these words.
