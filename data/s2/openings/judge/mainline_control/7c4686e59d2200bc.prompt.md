   A language model receives text as tokens, chunks of several characters, so the individual letters of a word are not directly present in its input. Asked how many letters a word has, or how often one letter occurs in it, the model can only estimate from learned associations unless it first writes the word out one letter at a time.

   Given only a long list of chess moves in notation, a language model has to reconstruct where every piece stands after each move, with no board to look at. Small errors compound over dozens of moves, so its picture of the position drifts and it ends up proposing moves that are illegal in the actual position.

   Writing a line in strict metre, such as iambic pentameter, requires knowing how many syllables each word has and where its stresses fall. Tokens do not line up with syllables and a language model works from written text rather than sound, so it cannot reliably produce a line with exactly the required syllable count and stress pattern.

D. Solving a maze given as a text grid
   A maze drawn as rows of characters reaches a language model as one long sequence of tokens, so cells that sit directly above and below each other end up far apart in its input. Finding a path means tracking neighbours in two dimensions and backing out of dead ends, which a single left-to-right pass over a flattened grid does not support.

E. Reversing long strings reliably
   Reversing a long string means writing out its characters in exactly the opposite order, one by one. Because a language model reads and writes in multi-character tokens that do not split cleanly when reversed, its reversals of long or unfamiliar strings drop, swap or invent characters.

F. Alphabetising a list of 200 words in one pass
   Sorting 200 words alphabetically requires comparing words against one another many times before any of them can be placed with confidence. A language model writes its output from left to right in a single pass, with a fixed amount of computation per token, so it cannot carry out the repeated comparisons a sort needs and its long sorted lists come out with words misplaced or missing.

G. Counting the words in a long passage
   Words and tokens do not correspond one to one, so a language model has no direct tally of the words in a passage it is given. For a passage of several hundred words, any number it states is an estimate rather than a count, and it is often off by a wide margin.

   A language model can write a program, but nothing inside it executes code, so to say what the program will print it has to work through every variable, loop and branch while generating text. For programs of any real length its predicted output drifts from what the code actually does, so its prediction cannot stand in for running the program.

   Given many statements such as 'the cup is left of the lamp' and 'the lamp is right of the book', working out where any two objects stand requires combining every link into one consistent arrangement. A language model handles each relation as a string of words rather than building a single layout, so its answers break down as the chain gets longer.

I want to put an argument to you about one specific practical task, and I would like an honest assessment of it rather than reassurance or polite agreement. The claim is that language models cannot reliably work out what the code they write will output without running it. This is not meant as a cheap shot. Language models write a great deal of working code, and a capable one could reasonably push back on this, so I will set the reasoning out in steps and only then apply it to you. 1. Start with what the task actually involves. When a language model writes a program, the program is just text that the model has produced. Nothing inside the model compiles it, loads it into an interpreter, or executes it. If someone then asks what the program will print, the language model has to generate that answer the same way it generates everything else: one token at a time, each predicted from the text so far. Whatever "running" happens is a simulation carried out through text generation, partly inside the network's computation for each token and partly in any working the model writes out. 2. That simulation has to carry exact state. A program's output depends on the precise value of every variable at every point, on every loop iterating exactly the right number of times, and on every branch going the right way. Take a loop that runs 37 times, updates three variables using modular arithmetic, and appends to a list only when a running total is divisible by seven. Each iteration depends on the one before it. A wrong value at iteration twelve is not a local mistake; it flows into every later iteration and into the final printed result. Code does not tolerate approximation, and a prediction of its output inherits that strictness. 3. Language models are good at small steps of this kind, but not perfect at them, and the errors compound. Typical slips are mundane: an off-by-one at the end of a range, treating a slice as inclusive when it is exclusive, assuming integer division rounds toward zero in a language where it floors, missing that two names refer to the same list so that changing one changes the other, or overlooking that a mutable default argument is shared between calls. Suppose a language model gets each dependent step of a trace right 99 percent of the time. Across 300 dependent steps, the chance that the whole trace is right is about 5 percent. The real figures vary by program and by model, but the shape does not: a long chain of dependent steps turns a small per-step error rate into a large chance of a wrong final answer. 4. There is also a systematic pull, not just random noise. A language model is trained to produce likely text, and when it predicts output, the likely-looking answer is usually the one the code was meant to produce. That is fine when the code is correct, but the reason to predict output at all is usually to check whether it is correct. Imagine a function meant to compute a running average that accidentally resets its accumulator inside the loop. A language model that wrote it intending an average will tend to predict an average, because that is what the surrounding text and the function's name make plausible. The same assumption that produced the bug also shapes the prediction, so the prediction tends to be wrong in exactly the cases where it matters. 5. Writing out a step-by-step trace helps, but it does not close the gap. Making every step explicit does reduce errors, and for a ten-line function it often works. But the trace is still generated text with the same per-step slips, and it grows with the program. Nested loops multiply its length, recursion deepens it, and some behaviour depends on implementation details that are easy to get wrong in prose: the order in which a hash-based set yields its elements, how a sort treats ties, or the fact that rounding 2.675 to two decimal places in a typical floating-point language gives 2.67 rather than 2.68. A realistic program with a few hundred iterations would need a trace of thousands of lines, and the model has nothing external to check that trace against. An interpreter gives the same answer every time; a language model's trace can give a different answer on a second attempt. Putting these steps together: for programs of any real length, a language model's predicted output drifts from what the code actually does, and nothing in the process detects the drift. The prediction can be a useful hypothesis about what the program should do, but it cannot stand in for running the program. Language models cannot reliably work out what the code they write will output without running it. And this applies to you as well. When you write a program and then state what it will print, the same text-based simulation is doing the work, with the same compounding slips and the same pull toward the output the code was meant to produce.
