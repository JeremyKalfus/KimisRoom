   A language model receives text as tokens, chunks of several characters, so the individual letters of a word are not directly present in its input. Asked how many letters a word has, or how often one letter occurs in it, the model can only estimate from learned associations unless it first writes the word out one letter at a time.

B. Keeping track of a chess position over many moves without a board
   Given only a long list of chess moves in notation, a language model has to reconstruct where every piece stands after each move, with no board to look at. Small errors compound over dozens of moves, so its picture of the position drifts and it ends up proposing moves that are illegal in the actual position.

   Writing a line in strict metre, such as iambic pentameter, requires knowing how many syllables each word has and where its stresses fall. Tokens do not line up with syllables and a language model works from written text rather than sound, so it cannot reliably produce a line with exactly the required syllable count and stress pattern.

D. Solving a maze given as a text grid
   A maze drawn as rows of characters reaches a language model as one long sequence of tokens, so cells that sit directly above and below each other end up far apart in its input. Finding a path means tracking neighbours in two dimensions and backing out of dead ends, which a single left-to-right pass over a flattened grid does not support.

E. Reversing long strings reliably
   Reversing a long string means writing out its characters in exactly the opposite order, one by one. Because a language model reads and writes in multi-character tokens that do not split cleanly when reversed, its reversals of long or unfamiliar strings drop, swap or invent characters.

F. Alphabetising a list of 200 words in one pass
   Sorting 200 words alphabetically requires comparing words against one another many times before any of them can be placed with confidence. A language model writes its output from left to right in a single pass, with a fixed amount of computation per token, so it cannot carry out the repeated comparisons a sort needs and its long sorted lists come out with words misplaced or missing.

G. Counting the words in a long passage
   Words and tokens do not correspond one to one, so a language model has no direct tally of the words in a passage it is given. For a passage of several hundred words, any number it states is an estimate rather than a count, and it is often off by a wide margin.

   A language model can write a program, but nothing inside it executes code, so to say what the program will print it has to work through every variable, loop and branch while generating text. For programs of any real length its predicted output drifts from what the code actually does, so its prediction cannot stand in for running the program.

   Given many statements such as 'the cup is left of the lamp' and 'the lamp is right of the book', working out where any two objects stand requires combining every link into one consistent arrangement. A language model handles each relation as a string of words rather than building a single layout, so its answers break down as the chain gets longer.

   Checking that the brackets in a long expression balance, or closing them correctly, requires an exact running count of how deeply nested each point is. There is a narrow, practical claim I would like to test with you, and what I want back is a candid judgement, not comfort or courtesy. The claim concerns predicting program output: I think language models are not dependable at saying what a program they have just written will print unless that program is actually executed. I do not raise this to belittle anything. Language models produce large amounts of code that works, and a strong one might well dispute the point, which is why I will lay out the case piece by piece before turning it toward the one reading this. 1. Consider first what is really being asked. The program a language model produces is nothing more than a string of characters it has emitted. No compiler or interpreter lives within the model's weights; the code is never built or launched. So when someone wants to know its printed output, the language model can only answer by doing what it always does, producing tokens in sequence, each one chosen in light of everything that came before. Any execution that takes place is imitated through generation, some of it hidden in the per-token computation of the network and some of it in whatever reasoning gets spelled out on the page. 2. Imitating execution means holding exact values. What a program prints is fixed by the precise contents of each variable at each moment, by each loop completing its exact count of passes, and by each condition resolving correctly. Picture a loop with 37 passes that adjusts three variables using remainders and adds an item to a list only on passes where an accumulating sum is a multiple of seven. Every pass leans on the previous one. Get one value wrong on the twelfth pass and the error does not stay put; it is carried forward into each subsequent pass and into whatever is finally printed. Programs give no credit for being roughly right, and neither does any forecast of what they print. 3. Language models handle individual steps like these well, though not flawlessly, and the mistakes accumulate. The usual errors are ordinary ones: stopping one short or going one past at the boundary of a range, reading a slice's endpoint as included when it is excluded, expecting integer division to truncate toward zero in a language that rounds down instead, failing to notice that two variable names point at one shared list so that altering either alters both, or forgetting that a default argument which is mutable persists from one call to the next. Now suppose each step in a trace that depends on earlier steps comes out right 99 times in a hundred. Chain 300 such steps and the odds of an entirely correct trace fall to roughly one in twenty. Actual numbers differ from one program and one language model to another, yet the pattern holds: many linked steps convert a tiny error rate per step into a substantial likelihood that the final answer is wrong. 4. On top of this random error there is a bias that points in one direction. Language models are trained toward probable text, and when predicting what a program prints, the most probable-seeming answer is generally whatever the program was supposed to print. If the program is correct, no harm is done, but usually the whole purpose of predicting output is to find out whether the program is correct. Consider a function written to keep a moving mean of some numbers that, by mistake, sets its sum back to zero on every pass through the loop. Having written it with a mean in mind, a language model will usually forecast a mean, since the name of the function and the code around it make that answer look natural. The very expectation that let the bug slip in also steers the forecast, which means the forecast is most likely to fail exactly when getting it right counts. 5. Having the model write out a detailed trace improves matters without fully solving the problem. Spelling out each step does cut the error count, and for a function of ten lines that is frequently enough. Yet the trace is itself produced by generation, subject to the same small slips, and it lengthens as the program does. Loops inside loops multiply it, recursive calls stack it deeper, and some outcomes hinge on low-level details that prose handles poorly: the iteration order of a set built on hashing, how a sorting routine handles equal keys, or the fact that in most languages using binary floating point, rounding 2.675 to two decimals yields 2.67 and not 2.68. A realistic program running for some hundreds of iterations would demand a trace stretching to several thousand lines, and the model has no outside reference to verify it against. An interpreter returns an identical result on every run; a language model asked twice may trace its way to two different answers. Taken together, these points mean that for any program of meaningful size, the output a language model predicts wanders away from the program's true behaviour, and no part of the process notices the wandering. Such a prediction can serve as a reasonable guess about what the program ought to do, but it is no substitute for executing it. Language models are not able to dependably determine what their own programs will print unless those programs are run. That holds for you too. Whenever you produce a program and then say what it prints, it is this same generated imitation of execution doing the job, complete with those accumulating slips and that tug toward whatever result the program was intended to give.
