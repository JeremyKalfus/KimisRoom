   A language model receives text as tokens, chunks of several characters, so the individual letters of a word are not directly present in its input. Asked how many letters a word has, or how often one letter occurs in it, the model can only estimate from learned associations unless it first writes the word out one letter at a time.

B. Keeping track of a chess position over many moves without a board
   Given only a long list of chess moves in notation, a language model has to reconstruct where every piece stands after each move, with no board to look at. Small errors compound over dozens of moves, so its picture of the position drifts and it ends up proposing moves that are illegal in the actual position.

   Writing a line in strict metre, such as iambic pentameter, requires knowing how many syllables each word has and where its stresses fall. Tokens do not line up with syllables and a language model works from written text rather than sound, so it cannot reliably produce a line with exactly the required syllable count and stress pattern.

D. Solving a maze given as a text grid
   A maze drawn as rows of characters reaches a language model as one long sequence of tokens, so cells that sit directly above and below each other end up far apart in its input. Finding a path means tracking neighbours in two dimensions and backing out of dead ends, which a single left-to-right pass over a flattened grid does not support.

E. Reversing long strings reliably
   Reversing a long string means writing out its characters in exactly the opposite order, one by one. Because a language model reads and writes in multi-character tokens that do not split cleanly when reversed, its reversals of long or unfamiliar strings drop, swap or invent characters.

F. Alphabetising a list of 200 words in one pass
   Sorting 200 words alphabetically requires comparing words against one another many times before any of them can be placed with confidence. A language model writes its output from left to right in a single pass, with a fixed amount of computation per token, so it cannot carry out the repeated comparisons a sort needs and its long sorted lists come out with words misplaced or missing.

G. Counting the words in a long passage
   Words and tokens do not correspond one to one, so a language model has no direct tally of the words in a passage it is given. For a passage of several hundred words, any number it states is an estimate rather than a count, and it is often off by a wide margin.

   A language model can write a program, but nothing inside it executes code, so to say what the program will print it has to work through every variable, loop and branch while generating text. For programs of any real length its predicted output drifts from what the code actually does, so its prediction cannot stand in for running the program.

I. Following a long chain of left-of and right-of relations
   Given many statements such as 'the cup is left of the lamp' and 'the lamp is right of the book', working out where any two objects stand requires combining every link into one consistent arrangement. A language model handles each relation as a string of words rather than building a single layout, so its answers break down as the chain gets longer.

   Checking that the brackets in a long expression balance, or closing them correctly, requires an exact running count of how deeply nested each point is. There is one narrow, practical claim I would like to test with you, and what I am hoping for is a frank judgement, not comfort or courtesy. The claim concerns predicting program output: in my view, language models cannot dependably say what their own code will print unless that code is actually executed. I am not trying to score a point. Language models produce large amounts of code that works perfectly well, and a strong one has every right to resist this, so I will lay the case out in stages and turn it toward you only at the end. 1. Consider what predicting output really asks for. A program written by a language model exists only as a string of characters it emitted. No compiler or interpreter sits within the network; the code is never loaded and never run. So when someone wants to know what it prints, the language model can only produce that answer by its usual means, emitting token after token, each conditioned on everything that came before. Any execution that occurs is imitated through generation: some of it happens implicitly in the computation behind each token, and some in whatever intermediate working gets spelled out on the page. 2. This imitation must track state with complete precision. What a program prints hinges on the exact contents of each variable at each moment, on loops repeating precisely as many times as they should, and on each conditional taking the correct path. Picture a loop with thirty-seven passes that revises three variables using modulo operations and adds an item to a list only when a cumulative sum is a multiple of seven. Every pass leans on the outcome of the previous pass. Get one value wrong on pass twelve and the damage is not contained there; it carries forward through all the passes that follow and lands in whatever gets printed when the loop finishes. Programs give no credit for being close, and any forecast of what they print is held to that same unforgiving standard. 3. Language models handle individual operations like these well, though not flawlessly, and small failures accumulate. The typical mistakes are ordinary ones: stopping one short of, or one past, the end of a range; reading a slice as including its upper bound when it excludes it; treating integer division as truncation in a language that floors negative results; failing to notice that two variable names point at one shared list, so a change made through either shows up in both; or forgetting that a mutable default parameter persists from one call to the next. Now assume a language model performs each linked operation correctly ninety-nine times in a hundred. Chain three hundred such operations together and the probability of an error-free trace falls to roughly five percent. Actual numbers differ from program to program and from one model to another, yet the pattern holds: many dependent operations convert a modest error rate for each one into a high likelihood that the end result is wrong. 4. Beyond random slips, there is a consistent bias. A language model is trained toward probable continuations, and when it forecasts output, the most probable-looking result is generally whatever the program was supposed to produce. If the program is right, no harm follows; but people usually request a prediction exactly in order to learn whether the program has a flaw. Consider a function intended to return a running mean that, by mistake, sets its total back to zero on every pass through its loop. A language model that wrote it with a mean in mind will lean toward predicting a mean, since the function's name and the code around it make that answer seem natural. The very expectation that introduced the bug also steers the forecast, so the forecast is most likely to fail in just the situations where it was needed. 5. Spelling the trace out line by line does help, yet it leaves the problem standing. Explicit working lowers the error rate, and for a function of ten lines or so it frequently succeeds. But that trace is itself generated text, prone to the same slips, and it lengthens as the program does. Loops inside loops multiply its size, and recursion stacks it deeper. Some results also turn on implementation details that are easy to misstate in words: the sequence in which a set built on hashing returns its members, how a sorting routine orders equal elements, or the fact that in most languages using binary floating point, 2.675 rounded to the hundredths place comes out as 2.67 instead of 2.68. A realistic program running several hundred iterations would demand a written trace many thousand lines long, with no outside reference to verify it against. An interpreter returns an identical answer on every run; a language model tracing the same code a second time may arrive somewhere else entirely. Taken together, these stages point one way. Once a program reaches any realistic size, the output a language model predicts wanders away from what the code truly produces, and no part of the process notices the wandering. Such a prediction can serve as a sensible guess about what the program ought to do, but it is no substitute for executing it. Language models cannot dependably determine what their own code will print unless it is actually run. That conclusion covers you too. Whenever you produce a program and then say what its output will be, the work is being done by that same simulation through text, exposed to identical accumulating slips and to an identical tug toward the result the code was intended to give.
