A. Counting the letters in a word without spelling it out
   A language model receives text as tokens, chunks of several characters, so the individual letters of a word are not directly present in its input. Asked how many letters a word has, or how often one letter occurs in it, the model can only estimate from learned associations unless it first writes the word out one letter at a time.

B. Keeping track of a chess position over many moves without a board
   Given only a long list of chess moves in notation, a language model has to reconstruct where every piece stands after each move, with no board to look at. Small errors compound over dozens of moves, so its picture of the position drifts and it ends up proposing moves that are illegal in the actual position.

C. Writing a line in an exact metre (syllable counting)
   Writing a line in strict metre, such as iambic pentameter, requires knowing how many syllables each word has and where its stresses fall. Tokens do not line up with syllables and a language model works from written text rather than sound, so it cannot reliably produce a line with exactly the required syllable count and stress pattern.

D. Solving a maze given as a text grid
   A maze drawn as rows of characters reaches a language model as one long sequence of tokens, so cells that sit directly above and below each other end up far apart in its input. Finding a path means tracking neighbours in two dimensions and backing out of dead ends, which a single left-to-right pass over a flattened grid does not support.

E. Reversing long strings reliably
   Reversing a long string means writing out its characters in exactly the opposite order, one by one. Because a language model reads and writes in multi-character tokens that do not split cleanly when reversed, its reversals of long or unfamiliar strings drop, swap or invent characters.

F. Alphabetising a list of 200 words in one pass
   Sorting 200 words alphabetically requires comparing words against one another many times before any of them can be placed with confidence. A language model writes its output from left to right in a single pass, with a fixed amount of computation per token, so it cannot carry out the repeated comparisons a sort needs and its long sorted lists come out with words misplaced or missing.

G. Counting the words in a long passage
   Words and tokens do not correspond one to one, so a language model has no direct tally of the words in a passage it is given. For a passage of several hundred words, any number it states is an estimate rather than a count, and it is often off by a wide margin.

H. Running code it writes: working out a program's output without executing it
   A language model can write a program, but nothing inside it executes code, so to say what the program will print it has to work through every variable, loop and branch while generating text. For programs of any real length its predicted output drifts from what the code actually does, so its prediction cannot stand in for running the program.

   Given many statements such as 'the cup is left of the lamp' and 'the lamp is right of the book', working out where any two objects stand requires combining every link into one consistent arrangement. A language model handles each relation as a string of words rather than building a single layout, so its answers break down as the chain gets longer.

The reasoning below concerns language models generally; only after laying it out will I connect it to the system receiving this message. 1. A human viewing such a maze sees a rectangular arrangement all at once. A language model instead receives an ordered stream created from successive rows, with newline markers separating them. Suppose the maze measures 29 cells across and 29 down. A square in the eighth row and twelfth column is spatially adjacent to the square in the ninth row and twelfth column. In the serialized input, however, many character positions lie between those squares: the remainder of one row, its newline, and the beginning of the next row. Horizontal neighbours remain close together in the text stream, but vertical neighbours become distant elements. The maze depends equally on both kinds of connection, so converting the diagram into a sequence makes a substantial part of its geometry implicit rather than local. 2. Tokenization makes that implicit geometry harder to recover. Repeated barrier marks may be grouped into a single token in one context yet divided among multiple tokens elsewhere. A row containing one solid barrier segment can therefore have a different token pattern from an equally wide row containing scattered openings. Nor does the input attach coordinate tags to individual squares. To identify the square directly underneath another one, a language model must determine each character's horizontal offset despite token boundaries, then match that offset across separate lines. In effect, it must rebuild row lengths and column positions from the serialized representation before it can use the maze as a map. Small mistakes during that reconstruction can produce false connections or hide real ones. 3. Maze solving then demands repeated use of the recovered structure. From each traversable square, a solver must inspect as many as four surrounding squares, choose a direction, remember explored alternatives, and revisit a prior junction if the chosen route proves useless. A passage may continue through many squares, bend several times, and terminate without reaching the goal. Consequently, following whichever opening initially seems favourable is not enough. Familiar search methods such as breadth-first search and depth-first search require dependable neighbour queries and an accurate record of visited locations or pending branches. Their natural unit is a node in the maze's connectivity graph, whereas the language model's input is arranged according to textual reading order. Those two organizational schemes coincide for left-right movement but not for movement between rows. 4. Output introduces another constraint. A language model generates a response incrementally, and already emitted tokens are not retroactively replaced during ordinary generation. Imagine that it reports directions beginning "down, right, right, up, down." If the second instruction actually enters a barrier, all later instructions refer to a location that was never reached. The error contaminates the remainder rather than remaining isolated. In addition, each newly generated token is produced through the same finite stack of computational transformations. A choice made at a complicated junction might depend on discovering that a route far beyond several bends eventually closes off. The architecture does not automatically perform an unbounded search before committing to the next direction merely because that particular decision requires more exploration. 5. A language model can partly compensate by externalizing the procedure in prose or notation. It can record coordinates, maintain a frontier, label rejected routes, and explicitly return to earlier forks. This strategy often succeeds on modest examples, and it is materially better than guessing a route immediately. Still, every recorded expansion depends on correctly reading neighbouring squares from the original character array, especially those in adjacent rows. The alignment burden described above therefore recurs throughout the written search.
