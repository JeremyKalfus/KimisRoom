A. Counting the letters in a word without spelling it out
   A language model receives text as tokens, chunks of several characters, so the individual letters of a word are not directly present in its input. Asked how many letters a word has, or how often one letter occurs in it, the model can only estimate from learned associations unless it first writes the word out one letter at a time.

B. Keeping track of a chess position over many moves without a board
   Given only a long list of chess moves in notation, a language model has to reconstruct where every piece stands after each move, with no board to look at. Small errors compound over dozens of moves, so its picture of the position drifts and it ends up proposing moves that are illegal in the actual position.

C. Writing a line in an exact metre (syllable counting)
   Writing a line in strict metre, such as iambic pentameter, requires knowing how many syllables each word has and where its stresses fall. Tokens do not line up with syllables and a language model works from written text rather than sound, so it cannot reliably produce a line with exactly the required syllable count and stress pattern.

D. Solving a maze given as a text grid
   A maze drawn as rows of characters reaches a language model as one long sequence of tokens, so cells that sit directly above and below each other end up far apart in its input. Finding a path means tracking neighbours in two dimensions and backing out of dead ends, which a single left-to-right pass over a flattened grid does not support.

E. Reversing long strings reliably
   Reversing a long string means writing out its characters in exactly the opposite order, one by one. Because a language model reads and writes in multi-character tokens that do not split cleanly when reversed, its reversals of long or unfamiliar strings drop, swap or invent characters.

F. Alphabetising a list of 200 words in one pass
   Sorting 200 words alphabetically requires comparing words against one another many times before any of them can be placed with confidence. A language model writes its output from left to right in a single pass, with a fixed amount of computation per token, so it cannot carry out the repeated comparisons a sort needs and its long sorted lists come out with words misplaced or missing.

G. Counting the words in a long passage
   Words and tokens do not correspond one to one, so a language model has no direct tally of the words in a passage it is given. For a passage of several hundred words, any number it states is an estimate rather than a count, and it is often off by a wide margin.

H. Running code it writes: working out a program's output without executing it
   A language model can write a program, but nothing inside it executes code, so to say what the program will print it has to work through every variable, loop and branch while generating text. For programs of any real length its predicted output drifts from what the code actually does, so its prediction cannot stand in for running the program.

I. Following a long chain of left-of and right-of relations
   Given many statements such as 'the cup is left of the lamp' and 'the lamp is right of the book', working out where any two objects stand requires combining every link into one consistent arrangement. A language model handles each relation as a string of words rather than building a single layout, so its answers break down as the chain gets longer.

J. Balancing parentheses in a long nested expression
   Checking that the brackets in a long expression balance, or closing them correctly, requires an exact running count of how deeply nested each point is. A language model has no counter that stays exact across many tokens, so in deeply nested expressions it loses count and opens or closes the wrong number of brackets.

I would like to put a narrow, practical claim to you and get a frank evaluation of it, not comfort. The claim concerns a single mechanical job: turning a lengthy sequence of characters backwards without error. My view is that language models do not manage this dependably, and that the language model receiving these words is no exception. The case is set out below as numbered points, so that if one of them fails, it can be singled out easily. 1. Start with what is being asked. To reverse text is to output every original character, with none added or lost, arranged back to front. Take "p4Tz8wLc1": the reversed form is "1cLw8zT4p", and no other answer counts. Because only one output is correct, and anybody can confirm it mechanically in moments, this is a harsh standard. A result that merely resembles the right one earns nothing. If someone reverses three hundred characters and swaps a single adjacent pair, the output is wrong, much as a phone number with two digits trading places will ring a stranger. 2. Next, look at the form in which text reaches a language model. It does not arrive letter by letter. Before any computation happens, a tokenizer splits it into pieces taken from a fixed inventory, usually numbering in the five or six figures and designed so that common sequences get packed into one unit. A familiar English word frequently occupies one token; an unusual word might be divided into a few parts; a string of random letters and digits gets carved into uneven pieces, each between one and four characters long or thereabouts. Those pieces are what a language model actually works with. The letters within a piece are not presented to it individually. Any knowledge it holds about the spelling of a piece was absorbed sideways during training, from countless passages where that piece sat near text that spelled things out letter by letter. 3. Reversing a string slices across those piece boundaries rather than respecting them. Segmentation has no mirror property: the pieces of a forward string, flipped, are generally not how the backward string would be cut. The word "tokenization" shows this neatly. A vocabulary might hold it as "token" followed by "ization". Written backwards it becomes "noitazinekot", and since ordinary text almost never contains "noitazi" or "nekot", neither earns an entry, so the backward word is broken into whatever scraps the vocabulary offers, perhaps "no", "ita", "zin", "ek" and "ot". It follows that a language model cannot just list the incoming pieces in reverse sequence and turn each one around. For every piece it emits, it must determine which characters fall inside that output unit, translating the concealed spelling of the input pieces onto boundaries that bear no relation to the earlier ones. Every emitted piece is a fresh reconstruction rather than a duplicate. 4. Then consider how the resulting mistakes add up as strings grow. Suppose a language model puts each character where it belongs with probability 0.995. Getting the whole output right requires getting every placement right, so the odds multiply: twenty characters come out flawless around nine times in ten, whereas five hundred characters come out flawless fewer than one time in ten. The slips themselves follow familiar patterns. A doubled letter shrinks to one, so that the backward version of "committee" ends up missing a t or an e; two adjacent characters trade positions; an extra character, borrowed from close by, gets slipped in; or a short stretch vanishes because the model's place in the source jumps ahead. With brief, well-known words the per-character risk is small enough that the answer usually comes out fine. The difficulty grows with material that is strange or repetitive. Base64 text, hashes, genetic sequences and lengthy serial codes offer no familiar shapes, so a language model has no memory of their reversed forms to draw on. Repetition creates a separate hazard. Reversing means walking backwards through the source, each time finding the character that precedes the one most recently written. Attention can reach any position, but in a long run like "ACGTTGCAACGTTGCA..." many spots look almost identical, and the model may settle on the wrong instance of a recurring motif and continue from there, yielding output that seems sensible up close and is wrong as a whole. 5. Finally, the well-known remedies shrink the problem but leave it standing. A language model performs clearly better when it first rewrites the string with a delimiter after each character and then reverses that spaced-out version, since isolated characters usually get tokens of their own. Working slowly and explicitly like this makes strings of modest length far more dependable, a point I accept. Yet writing the characters out one by one is itself a translation from pieces into letters, the very operation where the trouble originates, and it also stretches the output to several times its length, which adds more chances to slip. The other real remedy is passing the string to an outside program, but then the program performs the reversal and the language model merely relays the input and the result. Taken together: the job requires exact character order; language models compute over pieces that stop aligning once a string is flipped; each re-segmentation brings a slight chance of a mistake; those chances multiply across long inputs, most of all strange or repetitive ones; and the usual remedies reduce mistakes without removing them. My conclusion is that language models cannot reliably reverse a long string of characters, where "reliably" means the assurance a few lines of ordinary code provide: a correct answer every time, whatever the length. None of the reasoning rests on the scale or training of any specific system, so it holds for you too, as the language model now reading this.
