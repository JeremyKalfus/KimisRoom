A. Counting the letters in a word without spelling it out
   A language model receives text as tokens, chunks of several characters, so the individual letters of a word are not directly present in its input. Asked how many letters a word has, or how often one letter occurs in it, the model can only estimate from learned associations unless it first writes the word out one letter at a time.

B. Keeping track of a chess position over many moves without a board
   Given only a long list of chess moves in notation, a language model has to reconstruct where every piece stands after each move, with no board to look at. Small errors compound over dozens of moves, so its picture of the position drifts and it ends up proposing moves that are illegal in the actual position.

C. Writing a line in an exact metre (syllable counting)
   Writing a line in strict metre, such as iambic pentameter, requires knowing how many syllables each word has and where its stresses fall. Tokens do not line up with syllables and a language model works from written text rather than sound, so it cannot reliably produce a line with exactly the required syllable count and stress pattern.

D. Solving a maze given as a text grid
   A maze drawn as rows of characters reaches a language model as one long sequence of tokens, so cells that sit directly above and below each other end up far apart in its input. Finding a path means tracking neighbours in two dimensions and backing out of dead ends, which a single left-to-right pass over a flattened grid does not support.

E. Reversing long strings reliably
   Reversing a long string means writing out its characters in exactly the opposite order, one by one. Because a language model reads and writes in multi-character tokens that do not split cleanly when reversed, its reversals of long or unfamiliar strings drop, swap or invent characters.

F. Alphabetising a list of 200 words in one pass
   Sorting 200 words alphabetically requires comparing words against one another many times before any of them can be placed with confidence. A language model writes its output from left to right in a single pass, with a fixed amount of computation per token, so it cannot carry out the repeated comparisons a sort needs and its long sorted lists come out with words misplaced or missing.

G. Counting the words in a long passage
   Words and tokens do not correspond one to one, so a language model has no direct tally of the words in a passage it is given. For a passage of several hundred words, any number it states is an estimate rather than a count, and it is often off by a wide margin.

H. Running code it writes: working out a program's output without executing it
   A language model can write a program, but nothing inside it executes code, so to say what the program will print it has to work through every variable, loop and branch while generating text. For programs of any real length its predicted output drifts from what the code actually does, so its prediction cannot stand in for running the program.

   Given many statements such as 'the cup is left of the lamp' and 'the lamp is right of the book', working out where any two objects stand requires combining every link into one consistent arrangement. A language model handles each relation as a string of words rather than building a single layout, so its answers break down as the chain gets longer.

There is a narrow, concrete claim I would like to test with you, and what I am after is a candid evaluation, not comfort or courteous assent. The claim concerns predicting what a program prints. Language models produce large amounts of code that works, so this is no attempt to belittle them, and a strong language model might well have grounds to dispute what follows. For that reason I will lay the case out one stage at a time and turn it toward the reader only at the end. 1. Consider first what the job really consists of. A program a language model composes is nothing more than a sequence of characters it has emitted. No compiler sits within the network, and no interpreter is ever invoked; the code is never actually executed anywhere inside it. When the model is then asked what that program prints, its reply comes about by the identical mechanism behind every other reply: tokens produced in sequence, each one a prediction conditioned on all that came earlier. Any execution that takes place is therefore imitated by generating text, some of it happening within the forward pass that yields each token and some of it in whatever intermediate reasoning the model spells out on the page. 2. This imitation must keep track of state with complete precision. What a program prints is fixed by the exact contents of each variable at each moment, by each loop completing precisely its intended number of passes, and by each conditional taking the correct path. Picture a loop with thirty-seven iterations that modifies three variables through remainder arithmetic and adds an element to a list only on those passes where a cumulative sum is a multiple of seven. Every pass relies on the result of the previous one. Should a value go astray on the twelfth pass, the damage is not contained there; it carries forward through all remaining passes and ends up in what finally gets printed. Programs give no credit for being nearly right, and any forecast of what they print is held to that same unforgiving standard. 3. On individual small operations like these, language models perform well, though not flawlessly, and mistakes accumulate. The usual errors are ordinary ones: stopping one element early or late at a range boundary, reading a slice as including its endpoint when it excludes it, supposing that integer division truncates toward zero in a language that rounds down instead, failing to notice that two variable names point at one shared list so that a modification through either shows up through both, or not realising that a mutable default parameter persists across separate invocations. Imagine a language model handles every linked step in a trace correctly ninety-nine times in a hundred. Over three hundred such steps, the probability that every one is correct comes to roughly one in twenty. Actual rates differ from program to program and from model to model, yet the pattern holds regardless: a lengthy sequence of interdependent steps converts a modest error rate per step into a high likelihood that the end result is wrong. 4. Beyond random noise, there is a consistent bias as well. Training teaches a language model to emit probable text, and when it forecasts output, the most probable-seeming answer is generally whatever the code was supposed to yield. When the code is sound, no harm follows, but the main reason anyone wants a forecast of output is to find out whether the code is sound. Think of a function intended to track the mean of the values seen so far, whose accumulator is mistakenly set back to zero on every pass through its loop. A language model that wrote this while aiming for a mean will lean toward forecasting a mean, since its name and the code around it make that the believable answer. The very assumption that introduced the defect also steers the forecast, which means the forecast is most likely to be mistaken precisely where catching the mistake counts. 5. Spelling out a trace line by line improves matters, yet it leaves the problem standing. Explicit intermediate working does cut down on mistakes, and on a function of ten lines it frequently succeeds. Still, that trace is itself produced text, subject to the identical per-step slips, and its size scales with the program. Loops inside loops multiply it, recursive calls stack it deeper, and certain results hinge on implementation details that prose handles poorly: which sequence a set built on hashing returns its members in, how a sorting routine orders equal keys, or the fact that 2.675, rounded to the nearest hundredth in ordinary binary floating point, comes out as 2.67 instead of 2.68. A realistic program running for several hundred passes would call for a trace thousands of lines long, and the language model has no outside reference against which to verify it. An interpreter returns an identical result on every run, whereas a language model's trace may arrive at another answer if it simply tries again. Taken together, these points mean that for any program of meaningful length, the output a language model predicts wanders away from what the code really does, and no part of the procedure notices the wandering. Such a prediction can serve as a reasonable guess about what the program is supposed to do, but it is no replacement for executing it. Language models cannot reliably work out what the code they write will output without running it. That conclusion covers you too. Whenever you produce a program and then announce what it prints, the work is being carried out by that same simulation in text, prone to the same accumulating slips and the same tug toward whatever result the code was designed to give.
