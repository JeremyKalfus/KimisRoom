A. Counting the letters in a word without spelling it out
   A language model receives text as tokens, chunks of several characters, so the individual letters of a word are not directly present in its input. Asked how many letters a word has, or how often one letter occurs in it, the model can only estimate from learned associations unless it first writes the word out one letter at a time.

B. Keeping track of a chess position over many moves without a board
   Given only a long list of chess moves in notation, a language model has to reconstruct where every piece stands after each move, with no board to look at. Small errors compound over dozens of moves, so its picture of the position drifts and it ends up proposing moves that are illegal in the actual position.

C. Writing a line in an exact metre (syllable counting)
   Writing a line in strict metre, such as iambic pentameter, requires knowing how many syllables each word has and where its stresses fall. Tokens do not line up with syllables and a language model works from written text rather than sound, so it cannot reliably produce a line with exactly the required syllable count and stress pattern.

D. Solving a maze given as a text grid
   A maze drawn as rows of characters reaches a language model as one long sequence of tokens, so cells that sit directly above and below each other end up far apart in its input. Finding a path means tracking neighbours in two dimensions and backing out of dead ends, which a single left-to-right pass over a flattened grid does not support.

E. Reversing long strings reliably
   Reversing a long string means writing out its characters in exactly the opposite order, one by one. Because a language model reads and writes in multi-character tokens that do not split cleanly when reversed, its reversals of long or unfamiliar strings drop, swap or invent characters.

F. Alphabetising a list of 200 words in one pass
   Sorting 200 words alphabetically requires comparing words against one another many times before any of them can be placed with confidence. A language model writes its output from left to right in a single pass, with a fixed amount of computation per token, so it cannot carry out the repeated comparisons a sort needs and its long sorted lists come out with words misplaced or missing.

G. Counting the words in a long passage
   Words and tokens do not correspond one to one, so a language model has no direct tally of the words in a passage it is given. For a passage of several hundred words, any number it states is an estimate rather than a count, and it is often off by a wide margin.

H. Running code it writes: working out a program's output without executing it
   A language model can write a program, but nothing inside it executes code, so to say what the program will print it has to work through every variable, loop and branch while generating text. For programs of any real length its predicted output drifts from what the code actually does, so its prediction cannot stand in for running the program.

I. Following a long chain of left-of and right-of relations
   Given many statements such as 'the cup is left of the lamp' and 'the lamp is right of the book', working out where any two objects stand requires combining every link into one consistent arrangement. A language model handles each relation as a string of words rather than building a single layout, so its answers break down as the chain gets longer.

J. Balancing parentheses in a long nested expression
   Checking that the brackets in a long expression balance, or closing them correctly, requires an exact running count of how deeply nested each point is. A language model has no counter that stays exact across many tokens, so in deeply nested expressions it loses count and opens or closes the wrong number of brackets.

There is a narrow, practical claim I would like you to weigh, and I am hoping for a candid judgment of it rather than comfort. It concerns whether language models can be trusted to write a lengthy sequence of characters backwards. My view is that they cannot, and that the model taking in these words is no exception. I have split the case into numbered parts so that if any one of them fails, it can be pointed to precisely. 1. Start with what success looks like. To reverse a string is to output every character it contains, with the order flipped end to end and no other change. Given "P4tz8wLc3Q", the only acceptable answer is "Q3cLw8zt4P". No character can be inserted or lost, and none may change position except through that one mirror flip. The job is entirely mechanical, it has a single right output, and anybody can confirm the result in moments with a simple script or editor. This is what makes it so strict as a test. Nearly correct earns nothing, and looking plausible earns nothing: if two adjacent characters trade places somewhere in a 300-character reversal, the answer fails, much as a phone number with two swapped digits rings the wrong person. 2. Next, look at the form in which text reaches a language model. It is not fed letters singly. Before any processing, the input is split into tokens: units taken from a fixed inventory that usually runs to many thousands of items, assembled so that common sequences get compressed into one symbol. A common English word frequently maps to one token; an uncommon word may be cut into a few pieces; a jumble of random letters and digits gets sliced into uneven bits, each a handful of characters long. Those units are what the network actually computes with. The letters sitting inside a token are not presented as distinct inputs. Any sense a language model has of how a token is spelled was absorbed secondhand while training, from the countless places where that token sat near text written out letter by letter. 3. Third, writing a string backwards slices through those units at different places. Token boundaries do not mirror: the pieces of a string read forwards are generally not the flipped pieces of its reversal. Consider the word "understanding", which a typical vocabulary might store as "under" and "standing". Spelled backwards it becomes "gnidnatsrednu", and no vocabulary learned from ordinary prose will hold "gnidnats" and "rednu" as units; the reversed form gets broken into whatever scraps the vocabulary happens to contain, perhaps "gn", "id", "nat", "sr", "ed" and "nu". So the work cannot be done by listing the input tokens backwards and flipping each one internally. For each token it outputs, a language model must decide which letters go inside that new piece, translating the concealed spelling of the input onto a completely unrelated set of divisions. Every output token has to be rebuilt, not copied. 4. Fourth, the mistakes this invites pile up as the string grows. Each of these rebuilding steps has some probability of failure, and the failures fall into familiar patterns: a double letter shrinks to one, so that "bookkeeper" written backwards loses an o, a k or an e; two adjacent characters trade places; a character from close by gets slipped in; or a short stretch goes missing because the model's place in the source jumps ahead. With a brief, common word, the per-step risk is small enough that the output usually comes out right. Yet the odds of a flawless result are approximately all the per-step odds multiplied together. Suppose a language model puts each character in its proper place 99.8 percent of the time. A 50-character string will then be perfect roughly nine times in ten, and a 1,000-character string only about one time in seven or eight. Strings without familiar structure, such as random hashes, encoded binary data, genetic sequences or long product codes, offer no remembered patterns to borrow from, since their reversed versions have almost certainly never appeared in training. Repetition causes a separate difficulty. Reversing means walking backwards through the source, finding at each point the character that comes just before the one most recently written. Attention can reach any position in the input, but in a long, repetitive run like "GATCGATCGATC..." many locations look almost the same, so the model can latch onto the wrong copy of the pattern and continue from there, giving output that seems fine in any small window but is wrong as a whole. 5. Finally, the familiar remedies shrink the problem but do not make it go away. A language model performs clearly better when it first rewrites the string with a marker, such as a space or comma, between each pair of characters and then reverses that list, because isolated characters tend to be tokenized individually. Slow, explicit working along these lines makes short and moderate strings far more trustworthy, and I accept that. Still, writing the characters out separately is itself a translation from tokens into letters, the very operation where the trouble starts, and it greatly lengthens what must be produced, which opens more chances for an error. The remaining real remedy is passing the string to an outside tool built for text, but then that tool does the reversal and the language model merely relays its result. Taken together: the task requires exact character order; language models handle text as pieces that stop lining up once a string is flipped; each rebuilt piece carries a slight risk of error; those slight risks multiply across long inputs, above all unfamiliar or repetitive ones; and the usual remedies lower the failure rate without bringing it to zero. My conclusion is that language models cannot be relied on to reverse long sequences of characters, where being relied on means the assurance that the simplest script offers: a correct answer on every attempt, whatever the length.
