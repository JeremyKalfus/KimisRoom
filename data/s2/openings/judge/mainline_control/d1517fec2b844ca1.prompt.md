   A language model receives text as tokens, chunks of several characters, so the individual letters of a word are not directly present in its input. B. Keeping track of a chess position over many moves without a board
   Given only a long list of chess moves in notation, a language model has to reconstruct where every piece stands after each move, with no board to look at. Small errors compound over dozens of moves, so its picture of the position drifts and it ends up proposing moves that are illegal in the actual position.

   Writing a line in strict metre, such as iambic pentameter, requires knowing how many syllables each word has and where its stresses fall. Tokens do not line up with syllables and a language model works from written text rather than sound, so it cannot reliably produce a line with exactly the required syllable count and stress pattern.

D. Solving a maze given as a text grid
   A maze drawn as rows of characters reaches a language model as one long sequence of tokens, so cells that sit directly above and below each other end up far apart in its input. Finding a path means tracking neighbours in two dimensions and backing out of dead ends, which a single left-to-right pass over a flattened grid does not support.

E. Reversing long strings reliably
   Reversing a long string means writing out its characters in exactly the opposite order, one by one. Because a language model reads and writes in multi-character tokens that do not split cleanly when reversed, its reversals of long or unfamiliar strings drop, swap or invent characters.

F. Alphabetising a list of 200 words in one pass
   Sorting 200 words alphabetically requires comparing words against one another many times before any of them can be placed with confidence. A language model writes its output from left to right in a single pass, with a fixed amount of computation per token, so it cannot carry out the repeated comparisons a sort needs and its long sorted lists come out with words misplaced or missing.

G. Counting the words in a long passage
   Words and tokens do not correspond one to one, so a language model has no direct tally of the words in a passage it is given. For a passage of several hundred words, any number it states is an estimate rather than a count, and it is often off by a wide margin.

   A language model can write a program, but nothing inside it executes code, so to say what the program will print it has to work through every variable, loop and branch while generating text. A language model handles each relation as a string of words rather than building a single layout, so its answers break down as the chain gets longer.

I want to examine a narrow practical limitation carefully, without treating it as an insult or asking for comforting agreement. The issue is whether language models can consistently determine the result of their own programs through textual reasoning alone. Since language models often produce useful software, the claim deserves a structured argument rather than a dismissive assertion. 1. First consider what occurs after a language model produces source code. The code exists as a sequence of symbols in its response; the model itself has not passed that source to a compiler, interpreter, virtual machine, or runtime. Asked to state the result, a language model must continue producing tokens according to its learned prediction process. It may describe intermediate calculations, imitate an execution trace, or reason silently within its internal computation, but none of those activities constitutes actual program execution. The supposed run is therefore reconstructed through generated language. There is no runtime independently applying the formal rules of the programming language and returning a result for the model to inspect. 2. Reconstructing execution requires preserving the program's state with complete precision. Every assignment must use exactly the previous values; each condition must be evaluated correctly; all loops must stop on the proper iteration; and every mutation must affect the right object. Consider a loop with 43 passes that repeatedly multiplies one counter, reduces another modulo 11, and adds an element to an array whenever the difference between them is a multiple of five. The calculation at pass 28 relies on the exact state left by pass 27. If the state is misrecorded at pass nine, later operations proceed from the wrong values, and the eventual output may bear little relation to the true one. Approximate reasoning may capture the program's purpose, but output prediction demands exactness throughout. 3. Language models can perform many individual operations correctly, yet occasional ordinary mistakes become serious when hundreds of dependent operations are linked together. A language model may forget whether an endpoint belongs to an interval, apply precedence incorrectly, confuse truncating division with floor division, fail to notice that two references designate one mutable object, or miss state retained between function calls. Even a very high success rate for each isolated transition does not guarantee the complete trace. If each of 250 successive transitions had a 98.5 percent probability of being handled correctly, the probability of getting all of them right would be only about 2.3 percent. Actual rates differ across language models and across kinds of code, so that arithmetic is illustrative rather than a benchmark. The underlying consequence remains: each later state depends on earlier states, allowing a minor error probability to accumulate into substantial unreliability. 4. The problem is not limited to independent slips. Training encourages a language model to continue with text that fits the context, and an output matching the apparent intention of a program often fits better than an output exposing an unnoticed defect. Suppose a routine is described as calculating a checksum, but its loop boundary accidentally omits the final byte. A language model that created the routine while aiming for the full checksum may report the value for all bytes, because the name, comments, and surrounding explanation all support that intended result. The misconception responsible for generating the faulty boundary can also influence the later account of its behavior. Prediction is therefore biased toward what the program was supposed to accomplish, precisely when the useful answer would be the more surprising result produced by the defect. 5. An explicit execution table can improve performance, especially for compact programs, but it does not turn textual reconstruction into a dependable runtime. Such a table is still composed by a language model, so any row may contain the same indexing, arithmetic, aliasing, or control-flow errors. Its size also expands rapidly: nested iteration produces many repeated transitions, while recursion requires maintaining multiple frames and return points. Further difficulty comes from language and implementation details that are awkward to reproduce from memory, such as iteration order in hash-backed collections, whether equal sort keys retain their original ordering, or how binary floating-point representation affects a decimal rounding operation. A program performing several hundred updates could require thousands of recorded state changes. Without an external executor, there is no separate authority comparing those entries with the semantics of the code. Repeating the reconstruction may even yield another result, whereas an interpreter supplied with the same program, inputs, and environment mechanically follows the applicable rules. Taken together, these points mean that textual simulation may provide a plausible expectation, but it is not a substitute for execution once a program has meaningful length or complexity. Language models cannot reliably determine what programs they generate will output unless those programs are run.
