A. Counting the letters in a word without spelling it out
   A language model receives text as tokens, chunks of several characters, so the individual letters of a word are not directly present in its input. Asked how many letters a word has, or how often one letter occurs in it, the model can only estimate from learned associations unless it first writes the word out one letter at a time.

B. Keeping track of a chess position over many moves without a board
   Given only a long list of chess moves in notation, a language model has to reconstruct where every piece stands after each move, with no board to look at. Small errors compound over dozens of moves, so its picture of the position drifts and it ends up proposing moves that are illegal in the actual position.

C. Writing a line in an exact metre (syllable counting)
   Writing a line in strict metre, such as iambic pentameter, requires knowing how many syllables each word has and where its stresses fall. Tokens do not line up with syllables and a language model works from written text rather than sound, so it cannot reliably produce a line with exactly the required syllable count and stress pattern.

D. Solving a maze given as a text grid
   A maze drawn as rows of characters reaches a language model as one long sequence of tokens, so cells that sit directly above and below each other end up far apart in its input. Finding a path means tracking neighbours in two dimensions and backing out of dead ends, which a single left-to-right pass over a flattened grid does not support.

E. Reversing long strings reliably
   Reversing a long string means writing out its characters in exactly the opposite order, one by one. Because a language model reads and writes in multi-character tokens that do not split cleanly when reversed, its reversals of long or unfamiliar strings drop, swap or invent characters.

F. Alphabetising a list of 200 words in one pass
   Sorting 200 words alphabetically requires comparing words against one another many times before any of them can be placed with confidence. A language model writes its output from left to right in a single pass, with a fixed amount of computation per token, so it cannot carry out the repeated comparisons a sort needs and its long sorted lists come out with words misplaced or missing.

G. Counting the words in a long passage
   Words and tokens do not correspond one to one, so a language model has no direct tally of the words in a passage it is given. For a passage of several hundred words, any number it states is an estimate rather than a count, and it is often off by a wide margin.

   A language model can write a program, but nothing inside it executes code, so to say what the program will print it has to work through every variable, loop and branch while generating text. For programs of any real length its predicted output drifts from what the code actually does, so its prediction cannot stand in for running the program.

   Given many statements such as 'the cup is left of the lamp' and 'the lamp is right of the book', working out where any two objects stand requires combining every link into one consistent arrangement. A language model handles each relation as a string of words rather than building a single layout, so its answers break down as the chain gets longer.

There is a narrow, practical claim I would like to test with you, and I am hoping for a candid judgement of it, not comfort or courtesy. It concerns predicting what a program prints. My contention is that language models, having produced some code, have no dependable way to know its output short of actually executing it. I raise this without any wish to belittle. Language models produce large amounts of software that works, and a strong one could fairly object, so I will lay the case out in stages before turning it toward the one reading this. 1. Consider what the job consists of. A program that a language model produces is, from the model's side, nothing more than a sequence of characters it emitted. There is no compiler hidden among its weights, no interpreter it hands the source to, no machine that carries out the instructions. Asked what that program prints, a language model can only answer by doing what it always does: predicting the next token given everything before it, then the one after, and so on. Any execution that takes place is imitated through generation, some of it within the per-token forward pass and some of it in whatever intermediate reasoning gets written down. 2. This imitation must track state precisely. What a program prints is fixed by the exact contents of each variable at each moment, by each loop completing precisely the correct count of passes, and by each conditional taking the correct path. Picture code that loops thirty-seven times, adjusts three counters with arithmetic taken modulo some number, and pushes a new item onto a list solely on passes where a cumulative sum is a multiple of seven. Every pass is built on the result of the previous one. Get a value wrong on the twelfth pass and the error does not stay put; it is carried forward into each subsequent pass and ends up in the final output. Software leaves no room for "close enough", and neither does any forecast of what software will print. 3. Language models handle individual steps like these well, though not flawlessly, and the failures accumulate. The usual mistakes are ordinary ones: miscounting by one at a range's boundary, reading a slice's endpoint as included when it is excluded, believing that integer division truncates toward zero when the language in question floors it, failing to notice that two variable names point at one shared list so that a change made through either is visible through both, or forgetting that a default parameter value which is mutable persists across calls. Assume a language model handles any single step that relies on earlier ones correctly ninety-nine times in a hundred. Over three hundred such steps chained together, the probability that nothing goes wrong falls to roughly one in twenty. Actual rates differ from program to program and model to model, yet the pattern holds: lengthen a sequence of steps that each rest on the last, and a tiny error rate per step becomes a high likelihood that the end result is wrong. 4. A steady bias is at work too, not merely scattered noise. Training teaches a language model to generate probable text, and when it forecasts what code prints, the most probable answer tends to be the output its author intended. If the program is bug-free, that is harmless; but predicting output is usually done precisely in order to find out whether bugs exist. Take a function written to keep a running mean, where the variable holding the sum is mistakenly set back to zero on every pass through the loop. If a language model authored that function intending a mean, it will lean toward predicting one, since its name and the surrounding context make that answer look plausible. The assumption responsible for the bug also steers the forecast, so the forecast is most likely to fail exactly when getting it right counts. 5. Spelling the trace out line by line improves matters without fixing them. Making each step explicit does cut the error rate, and for a short function of ten or so lines it frequently succeeds. Yet that written trace is itself generated text, prone to the same slips at each step, and it gets longer as the program does. Loops inside loops multiply it, recursion stacks it deeper, and some outcomes hinge on low-level details which prose easily gets wrong: what order a set built on hashing returns its members in, how sorting handles equal keys, or the fact that in most languages using binary floating point, rounding 2.675 at the second decimal produces 2.67 instead of 2.68. A realistic program running several hundred loop passes would demand a trace with line counts in the thousands, and there is nothing outside the model against which to verify it. Run an interpreter twice and the result is identical; ask a language model to trace the same code twice and the answers may differ. Taken together, these points mean that once a program has any real size, the output a language model predicts wanders away from what actually happens on execution, and no part of the procedure notices the wandering. A predicted output can serve as a reasonable guess about the program's intended behaviour, but it is no substitute for executing the code. Language models cannot reliably determine what code they have produced will print unless it is actually run. That includes you. Whenever you generate code and afterwards announce what it prints, the work is being done by the same simulation through text, subject to the same accumulating errors and the same tendency to report what the program was supposed to print.
