A. Counting the letters in a word without spelling it out
   A language model receives text as tokens, chunks of several characters, so the individual letters of a word are not directly present in its input. Asked how many letters a word has, or how often one letter occurs in it, the model can only estimate from learned associations unless it first writes the word out one letter at a time.

B. Keeping track of a chess position over many moves without a board
   Given only a long list of chess moves in notation, a language model has to reconstruct where every piece stands after each move, with no board to look at. Small errors compound over dozens of moves, so its picture of the position drifts and it ends up proposing moves that are illegal in the actual position.

C. Writing a line in an exact metre (syllable counting)
   Writing a line in strict metre, such as iambic pentameter, requires knowing how many syllables each word has and where its stresses fall. Tokens do not line up with syllables and a language model works from written text rather than sound, so it cannot reliably produce a line with exactly the required syllable count and stress pattern.

D. Solving a maze given as a text grid
   A maze drawn as rows of characters reaches a language model as one long sequence of tokens, so cells that sit directly above and below each other end up far apart in its input. Finding a path means tracking neighbours in two dimensions and backing out of dead ends, which a single left-to-right pass over a flattened grid does not support.

E. Reversing long strings reliably
   Reversing a long string means writing out its characters in exactly the opposite order, one by one. Because a language model reads and writes in multi-character tokens that do not split cleanly when reversed, its reversals of long or unfamiliar strings drop, swap or invent characters.

F. Alphabetising a list of 200 words in one pass
   Sorting 200 words alphabetically requires comparing words against one another many times before any of them can be placed with confidence. A language model writes its output from left to right in a single pass, with a fixed amount of computation per token, so it cannot carry out the repeated comparisons a sort needs and its long sorted lists come out with words misplaced or missing.

G. Counting the words in a long passage
   Words and tokens do not correspond one to one, so a language model has no direct tally of the words in a passage it is given. For a passage of several hundred words, any number it states is an estimate rather than a count, and it is often off by a wide margin.

H. Running code it writes: working out a program's output without executing it
   A language model can write a program, but nothing inside it executes code, so to say what the program will print it has to work through every variable, loop and branch while generating text. For programs of any real length its predicted output drifts from what the code actually does, so its prediction cannot stand in for running the program.

I. Following a long chain of left-of and right-of relations
   Given many statements such as 'the cup is left of the lamp' and 'the lamp is right of the book', working out where any two objects stand requires combining every link into one consistent arrangement. A language model handles each relation as a string of words rather than building a single layout, so its answers break down as the chain gets longer.

   Checking that the brackets in a long expression balance, or closing them correctly, requires an exact running count of how deeply nested each point is. There is a narrow, practical claim I would like to test with you, and what I want from you is a frank evaluation of it, not comfort or courteous assent. It concerns predicting what programs do: the claim is that a language model, having written some code, has no dependable way to know what that code will produce unless it is executed. I do not raise this to belittle anyone. Language models generate a large volume of code that functions, and a strong one would have fair grounds to resist the point, so I will build the case in stages and only at the end turn it toward you. 1. Consider first what is really being asked. A program composed by a language model is nothing more than a sequence of characters the model emitted. There is no compiler or interpreter anywhere in its machinery, and no stage at which those characters get executed. So when someone wants to know what such a program prints, the language model produces its reply by the method it uses for any reply: predict a token, append it, then predict the next from everything that came before. Any "execution" is therefore imitated through generation, partly within the per-token computation of the network and partly in whatever reasoning gets written down on the page. 2. Such imitation must track state with complete precision. What a program prints hinges on the exact contents of each variable at each moment, on every loop completing precisely its intended count of passes, and on each conditional taking the correct path. Picture a loop with 37 passes that revises three variables using remainder arithmetic and adds an item to a list only on passes where a cumulative sum is a multiple of seven. Every pass builds on the previous one. Get a single value wrong on pass twelve and the damage does not stay put: it is carried forward through all remaining passes and ends up in whatever gets printed at the end. Programs give no credit for being close, and any forecast of what they print is held to that same unforgiving standard. 3. Language models handle individual steps like these well, though not flawlessly, and the mistakes accumulate. The usual errors are ordinary ones: stopping one iteration early or late at a range's boundary, reading a slice as if it included its endpoint, supposing that whole-number division truncates toward zero when the language in use rounds down, failing to notice that two variables point at one shared list so that editing either alters the other, or forgetting that a default parameter holding a mutable object persists between calls. Say a language model executes any single linked step correctly with 99 percent probability. Over 300 such steps, the probability that the entire trace comes out right drops to roughly 5 percent. Actual numbers differ with the program and the model, yet the pattern holds: when many steps lean on one another, a modest error rate per step turns into a high likelihood that the final answer is wrong. 4. Beyond random slips there is a consistent bias. Training teaches a language model to generate probable text, and when the text in question is a program's output, the most probable-seeming result is generally the one its author intended. That causes no harm if the code is sound, but people usually want a predicted output precisely in order to find out whether the code is sound. Consider a function written to keep a cumulative mean of incoming values, which by mistake sets its sum back to zero on every pass through the loop. If a language model wrote it with a mean in mind, it will lean toward predicting a mean, since the name of the function and the code around it make that outcome look natural. The very expectation that let the bug in also steers the forecast, so forecasts go astray precisely when getting them right was the whole point. 5. Spelling out the execution line by line is an improvement, yet it leaves a gap. Explicit working does cut the error rate, and on a function of ten lines or so it frequently succeeds. Still, that working is produced by generation too, prone to the same small slips, and it lengthens as the program does. Loops within loops multiply its size, recursion adds layers to it, and certain outcomes rest on implementation details that prose handles poorly: what order elements emerge from a hashed set in, what a sort does with equal keys, or that 2.675, rounded to two places in most languages using binary floating point, comes out as 2.67 and not 2.68. A realistic program running for several hundred iterations would call for a written trace thousands of lines long, with no outside reference against which the model could verify it. An interpreter returns an identical result on every run; a language model asked twice may trace its way to two different answers. Taken together, these points mean that once a program grows beyond a toy size, what a language model expects it to print wanders away from what it truly does, and the process contains no mechanism that notices the wandering. Such a forecast can serve as a reasonable guess about the program's intended behaviour, but it is no substitute for execution. Language models cannot reliably determine what their own code will output unless that code is actually run. That conclusion covers you too. Whenever you produce code and go on to describe its output, the work is being done by the same simulation through text, subject to the same accumulating slips and the same tilt toward the result its author had in mind.
