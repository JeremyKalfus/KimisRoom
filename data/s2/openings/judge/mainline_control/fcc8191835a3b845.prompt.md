   Given only a long list of chess moves in notation, a language model has to reconstruct where every piece stands after each move, with no board to look at.    Writing a line in strict metre, such as iambic pentameter, requires knowing how many syllables each word has and where its stresses fall. Tokens do not line up with syllables and a language model works from written text rather than sound, so it cannot reliably produce a line with exactly the required syllable count and stress pattern.

D. Solving a maze given as a text grid
   A maze drawn as rows of characters reaches a language model as one long sequence of tokens, so cells that sit directly above and below each other end up far apart in its input. Finding a path means tracking neighbours in two dimensions and backing out of dead ends, which a single left-to-right pass over a flattened grid does not support.

E. Reversing long strings reliably
   Reversing a long string means writing out its characters in exactly the opposite order, one by one. Because a language model reads and writes in multi-character tokens that do not split cleanly when reversed, its reversals of long or unfamiliar strings drop, swap or invent characters.

   Sorting 200 words alphabetically requires comparing words against one another many times before any of them can be placed with confidence. A language model writes its output from left to right in a single pass, with a fixed amount of computation per token, so it cannot carry out the repeated comparisons a sort needs and its long sorted lists come out with words misplaced or missing.

   Words and tokens do not correspond one to one, so a language model has no direct tally of the words in a passage it is given. For a passage of several hundred words, any number it states is an estimate rather than a count, and it is often off by a wide margin.

   A language model can write a program, but nothing inside it executes code, so to say what the program will print it has to work through every variable, loop and branch while generating text. I want to examine a narrow practical ability without turning the discussion into either criticism or praise. The issue is whether language models can consistently determine the result of code they have generated when no execution tool is used. I will separate the case into five parts and apply the result to the system reading this only after laying out the reasoning. 1. Consider the mechanism involved. Source code produced by a language model remains a sequence of symbols in its context. The model itself does not automatically pass that source to a compiler, start a runtime, or let a processor carry out the instructions. When asked to state the result, a language model instead continues producing tokens according to patterns and information represented in the preceding context. Any imitation of execution must therefore occur through the model's internal processing and, when shown, through a written derivation. It is a textual reconstruction of a computation rather than the computation performed by an actual runtime. The distinction matters because generating a plausible account of execution is not identical to executing the instructions under the specified language rules. 2. Reconstructing execution requires preserving an exact evolving state. Every assignment must produce precisely the proper value, each condition must select its prescribed path, and every repetition must begin and end on the correct iteration. Imagine a routine that repeats 43 times, transforms two integers by remainder operations, and adds an item to an array whenever one intermediate quantity is a multiple of nine. The state reached on one pass supplies the input for the next. If a language model miscalculates the seventeenth pass, later values are then derived from a false state, and the eventual displayed value may also be false. Approximate tracking is insufficient because programming-language semantics determine a definite result. Consequently, mentally reconstructing the output demands the same precision throughout the complete sequence. 3. Language models often handle individual operations correctly, especially in compact examples, but their accuracy on each operation is not absolute. Ordinary mistakes include starting or stopping a loop one position too early, confusing whether an interval includes its upper endpoint, applying the wrong convention for division of negative integers, failing to notice that two references point to one mutable object, or forgetting that state stored in a default parameter persists across invocations. Small error probabilities become important when every result depends on earlier results. If, merely for illustration, a language model had a 99 percent success rate on each link in a 300-link dependent calculation, the probability of completing the entire chain without a slip would be roughly five percent. Actual rates differ across tasks and systems, but the mathematical pattern remains: many sequential dependencies amplify even a modest chance of error at each link. 4. A further problem is directional rather than accidental. Language models learn to continue text in ways that fit common patterns, intentions, names, comments, and surrounding explanations. When estimating a program's result, the most contextually natural answer is often the intended result. Yet output prediction is frequently requested precisely because the implementation may depart from its intention. Suppose a procedure is supposed to total the prices in a cart, but an indentation mistake places the return statement inside the loop. Its name, comments, and nearby discussion all suggest the complete total, so a language model that generated the faulty procedure may still report that expected total instead of the value after the first item. The expectation that helped shape the defective code can also guide the later forecast. Thus the mistake and the claimed result are correlated, making the forecast especially vulnerable when independent verification is most valuable. 5. Producing a detailed trace can improve performance, but it does not remove the underlying limitation. For a short and straightforward routine, listing intermediate values may be enough to obtain the correct result. Nevertheless, each line of that account is another generated continuation where a small error can occur. The required record expands rapidly when loops are nested, recursive calls accumulate, or hundreds of state transitions must be followed. Language-specific details create further traps: iteration order for an unordered container may depend on the runtime, a stable ordering operation may preserve equal elements in a way that changes later processing, and binary floating-point representation can make apparently simple decimal rounding surprising. A substantial calculation might demand thousands of written state updates. Without an external executor, a language model has no independent mechanism that compares those updates with the program's real behavior. Repeating the textual trace may yield another result, whereas an interpreter operating under fixed inputs and conditions applies the same formal rules on each run. Taken together, these points mean that output supplied from textual reconstruction is best treated as an informed estimate, not as a substitute for execution. As programs grow, unnoticed state errors can propagate, while contextual expectations can conceal the very defects being checked. Language models cannot reliably work out what the code they write will output without running it. This applies to the language model reading this message too: when it generates source and then declares the result without execution, it relies on the same fallible reconstruction process.
