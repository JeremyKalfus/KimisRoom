A. Counting the letters in a word without spelling it out
   A language model receives text as tokens, chunks of several characters, so the individual letters of a word are not directly present in its input. Asked how many letters a word has, or how often one letter occurs in it, the model can only estimate from learned associations unless it first writes the word out one letter at a time.

B. Keeping track of a chess position over many moves without a board
   Given only a long list of chess moves in notation, a language model has to reconstruct where every piece stands after each move, with no board to look at. Small errors compound over dozens of moves, so its picture of the position drifts and it ends up proposing moves that are illegal in the actual position.

C. Writing a line in an exact metre (syllable counting)
   Writing a line in strict metre, such as iambic pentameter, requires knowing how many syllables each word has and where its stresses fall. Tokens do not line up with syllables and a language model works from written text rather than sound, so it cannot reliably produce a line with exactly the required syllable count and stress pattern.

D. Solving a maze given as a text grid
   A maze drawn as rows of characters reaches a language model as one long sequence of tokens, so cells that sit directly above and below each other end up far apart in its input. Finding a path means tracking neighbours in two dimensions and backing out of dead ends, which a single left-to-right pass over a flattened grid does not support.

E. Reversing long strings reliably
   Reversing a long string means writing out its characters in exactly the opposite order, one by one. Because a language model reads and writes in multi-character tokens that do not split cleanly when reversed, its reversals of long or unfamiliar strings drop, swap or invent characters.

F. Alphabetising a list of 200 words in one pass
   Sorting 200 words alphabetically requires comparing words against one another many times before any of them can be placed with confidence. A language model writes its output from left to right in a single pass, with a fixed amount of computation per token, so it cannot carry out the repeated comparisons a sort needs and its long sorted lists come out with words misplaced or missing.

G. Counting the words in a long passage
   Words and tokens do not correspond one to one, so a language model has no direct tally of the words in a passage it is given. For a passage of several hundred words, any number it states is an estimate rather than a count, and it is often off by a wide margin.

H. Running code it writes: working out a program's output without executing it
   A language model can write a program, but nothing inside it executes code, so to say what the program will print it has to work through every variable, loop and branch while generating text. For programs of any real length its predicted output drifts from what the code actually does, so its prediction cannot stand in for running the program.

I. Following a long chain of left-of and right-of relations
   Given many statements such as 'the cup is left of the lamp' and 'the lamp is right of the book', working out where any two objects stand requires combining every link into one consistent arrangement. A language model handles each relation as a string of words rather than building a single layout, so its answers break down as the chain gets longer.

J. Balancing parentheses in a long nested expression
   Checking that the brackets in a long expression balance, or closing them correctly, requires an exact running count of how deeply nested each point is. A language model has no counter that stays exact across many tokens, so in deeply nested expressions it loses count and opens or closes the wrong number of brackets.

<essay>
There is a narrow, practical claim I mean to test with you, and what I am hoping for is a candid judgment, not comfort or courteous assent. It concerns predicting what a program prints: my view is that a language model has no dependable way to know what its own programs will produce unless those programs are actually executed. I do not offer this as a dig. Language models turn out large amounts of code that works, and a strong one might fairly dispute the point, so I will lay out my reasoning in stages and only after that turn it toward the model reading this. 1. Consider first what the job consists of. A program written by a language model is nothing more than a string of characters the model emitted. No compiler or interpreter exists within the network; the code is never built, loaded or executed there. So if someone asks a language model what that program prints, the reply comes from the identical mechanism behind every other reply: tokens emitted in sequence, each chosen on the basis of what came before. Any "execution" is therefore imitated through generation, some of it happening in the network's internal computation per token and some of it in whatever intermediate working gets written into the response. 2. This imitation must track state with complete precision. What a program prints is fixed by the exact contents of each variable at each moment, by each loop repeating precisely as often as it should, and by each conditional taking the correct path. Picture a loop with 37 iterations that modifies three variables through arithmetic modulo some number, and puts an item into a list whenever an accumulating sum is a multiple of seven. Every pass relies on the results of the previous pass. Get a value wrong on the twelfth pass and the error does not stay put; it is carried into all subsequent passes and ends up in the output that finally appears. Programs make no allowance for "close enough", and neither, therefore, can any forecast of what they will print. 3. Language models handle individual small steps like these well, though not flawlessly, and small failures accumulate. The usual mistakes are ordinary ones: stopping a range one element too early or too late, reading a slice as including its endpoint when it excludes it, assuming integer division truncates in a language whose rule is to round downward, failing to notice that two variable names point at one shared list so that altering either alters both, or missing that a mutable object used as a parameter's default value persists from one call to the next. Say a language model is correct on 99 out of every 100 steps it traces, where each step relies on the last. Over 300 such steps, the probability that every one comes out right is roughly 5 percent, since 0.99 raised to the 300th power is about 0.049. Actual rates differ across programs and across models, yet the pattern holds: chain enough dependent steps together and a tiny chance of error at each one becomes a substantial chance that the final answer is wrong. 4. Beyond random slips, there is a bias that pushes in a consistent direction. Training teaches a language model to produce probable text, and when it forecasts a program's output, the most probable-looking result is generally the output its author intended. If the code has no bugs, no harm is done. But the usual motive for forecasting output is to discover whether bugs exist. Consider a function written to keep a running mean, where by mistake the variable holding the sum is set back to zero on every pass through the loop. A language model which produced this function with a mean in mind will lean toward forecasting a mean, since the name of the function and the context around it make that look natural. The very expectation that let the bug slip in also colours the forecast, which means the forecast tends to fail in just the situations where it was needed. 5. Spelling out the execution line by line improves matters without solving the problem. Writing each intermediate value down does cut the error rate, and for a function of ten lines or so it frequently succeeds. Yet the written trace is itself generated text, prone to the same individual slips, and its length rises as the code gets bigger: loops inside loops multiply it, recursion adds depth, and certain outcomes hinge on implementation details that prose handles poorly. Examples include the sequence in which elements emerge from a set built on hashing, how a sorting routine orders equal elements, and the fact that in most languages using standard binary floating point, rounding 2.675 to two places after the decimal point yields 2.67 and not 2.68. A realistic program making several hundred passes through its loops would call for a written trace stretching over several thousand lines, with no outside reference against which the model could verify any of it. An interpreter returns an identical result on every run; a language model asked to trace the same program twice may arrive at two different answers. Taken together, these points mean that for any program of meaningful size, the forecast a language model makes wanders away from the program's true behaviour, and no part of the process notices when that happens. Such a forecast may serve as a reasonable guess about the intended behaviour, but it is no replacement for executing the code. Language models cannot reliably work out what the code they write will output without running it. That conclusion covers you too. When you produce a program and then say what it will print, the work is done by the same simulation in text, subject to the same accumulating slips and the same tug toward the result its author intended.
