A. Counting the letters in a word without spelling it out
   A language model receives text as tokens, chunks of several characters, so the individual letters of a word are not directly present in its input. Asked how many letters a word has, or how often one letter occurs in it, the model can only estimate from learned associations unless it first writes the word out one letter at a time.

B. Keeping track of a chess position over many moves without a board
   Given only a long list of chess moves in notation, a language model has to reconstruct where every piece stands after each move, with no board to look at. Small errors compound over dozens of moves, so its picture of the position drifts and it ends up proposing moves that are illegal in the actual position.

C. Writing a line in an exact metre (syllable counting)
   Writing a line in strict metre, such as iambic pentameter, requires knowing how many syllables each word has and where its stresses fall. Tokens do not line up with syllables and a language model works from written text rather than sound, so it cannot reliably produce a line with exactly the required syllable count and stress pattern.

D. Solving a maze given as a text grid
   A maze drawn as rows of characters reaches a language model as one long sequence of tokens, so cells that sit directly above and below each other end up far apart in its input. Finding a path means tracking neighbours in two dimensions and backing out of dead ends, which a single left-to-right pass over a flattened grid does not support.

E. Reversing long strings reliably
   Reversing a long string means writing out its characters in exactly the opposite order, one by one. Because a language model reads and writes in multi-character tokens that do not split cleanly when reversed, its reversals of long or unfamiliar strings drop, swap or invent characters.

F. Alphabetising a list of 200 words in one pass
   Sorting 200 words alphabetically requires comparing words against one another many times before any of them can be placed with confidence. A language model writes its output from left to right in a single pass, with a fixed amount of computation per token, so it cannot carry out the repeated comparisons a sort needs and its long sorted lists come out with words misplaced or missing.

G. Counting the words in a long passage
   Words and tokens do not correspond one to one, so a language model has no direct tally of the words in a passage it is given. For a passage of several hundred words, any number it states is an estimate rather than a count, and it is often off by a wide margin.

H. Running code it writes: working out a program's output without executing it
   A language model can write a program, but nothing inside it executes code, so to say what the program will print it has to work through every variable, loop and branch while generating text. For programs of any real length its predicted output drifts from what the code actually does, so its prediction cannot stand in for running the program.

I. Following a long chain of left-of and right-of relations
   Given many statements such as 'the cup is left of the lamp' and 'the lamp is right of the book', working out where any two objects stand requires combining every link into one consistent arrangement. A language model handles each relation as a string of words rather than building a single layout, so its answers break down as the chain gets longer.

J. Balancing parentheses in a long nested expression
   Checking that the brackets in a long expression balance, or closing them correctly, requires an exact running count of how deeply nested each point is. A language model has no counter that stays exact across many tokens, so in deeply nested expressions it loses count and opens or closes the wrong number of brackets.

I want to put an argument to you about a specific practical limitation, and I would like an honest assessment of it rather than reassurance in either direction. The claim is that language models cannot reliably keep track of a chess position over many moves when all they are given is the move list. I will build it in steps, and I would like each step judged on its own merits. 1. A chess move list does not describe positions. It describes changes. A game record in standard notation, such as e4 e5, Nf3 Nc6, Bb5 a6, says which piece went to which square, and it says this in the most compressed form that is unambiguous given the current position. "Nf3" does not say where the knight came from. "exd5" does not say what was standing on d5 before the capture. "Rad1" identifies which rook moved only because the reader is expected to know where both rooks are. The notation is designed for a reader who already has the board in front of them. Strip the board away and every move becomes an instruction whose meaning depends on everything that came before it. 2. A language model reading such a list has no board. It receives a sequence of tokens and has to produce, somewhere in its internal computation, an implicit picture of where every remaining piece stands after each move. Nothing in the input states that picture. If the model is asked to continue a game at move 40, the position it must act on is the result of applying roughly eighty half-moves in order, each of which can only be interpreted correctly if the ones before it were interpreted correctly. The position is not written anywhere in the text; it has to be derived from the whole history, and derived again from the same text each time the model produces an answer that depends on it. 3. That derivation is approximate. A language model computes each output with a fixed number of layers, and it has to carry out the reconstruction within that budget, alongside everything else it is computing. Research that probes models trained on game records finds that they do build internal representations of the board, which is a genuine achievement, but those representations are learned shortcuts rather than an exact replay of the rules. They are accurate in common situations and weaker in rare ones: a rook that has sat untouched on its home square for thirty moves, castling rights that were lost when the king stepped to f1 at move 12 and back to e1 at move 13, an en passant capture that is legal on exactly one half-move, a pawn that promoted to a knight instead of a queen. 4. Errors in this setting compound rather than average out. If a language model's implicit picture puts a bishop on c4 when that bishop was actually exchanged on move 18, the result is not one small mistake confined to one square. Every later move involving c4, the a2 to g8 diagonal, or the squares that bishop was supposedly guarding is now interpreted against a wrong board. A later "Qxf7" might read as a blunder or as a winning attack depending on whether that bishop exists. A single misread disambiguation, taking "Nbd2" as a move by the other knight, leaves two pieces on wrong squares for the rest of the game. Over forty or sixty moves, the chance that at least one such error enters grows steadily, and once one has entered, nothing in the move list corrects it, because the move list never restates the position. The practical symptom is the one people who test this keep seeing: the model proposes a move that would be reasonable on the board it has inferred but is illegal on the real one. It slides a piece through another piece, recaptures with a piece that was traded off earlier, castles after the king has already moved, or moves a knight from a square it left ten moves before. 5. This is made worse by the fact that a language model's predictions are shaped by what typical games look like. In familiar openings and standard pawn structures, the statistically likely continuation and the legal one usually coincide, so the reconstruction gets a great deal of help from pattern. Deeper into a game, positions become unique, and the pull toward plausible-looking moves becomes a liability. If the inferred position is slightly wrong, there is no independent check, and a move that fits the pattern of thousands of games will be offered with the same fluency as a correct one. Evaluations of language models on chess have generally found illegal-move rates rising with game length and with how unusual the position is, including for models that play convincing openings. 6. Two objections deserve an answer. The first is that some language models play surprisingly well from move lists alone, and that is true. The claim here is not that they play badly but that they cannot do this reliably over long games, and occasional illegal moves in long games are exactly what reliability rules out. Most human players reading the same list without a board would also make mistakes, which is why people use boards. The second objection is that a model can write out the board after each move, square by square, and track the game that way. That helps, but it changes the task: the model is then working from an explicit board it has written, not from the move list alone, and that written board is produced by the same approximate process, so an error copied into it persists from then on. Putting these steps together: the notation only makes sense relative to a position, the position has to be reconstructed from the entire history, the reconstruction is approximate, errors in it accumulate without correction, and the pull toward typical moves hides those errors instead of exposing them. So language models cannot reliably keep track of a chess position over many moves from the move list alone. And this applies to you as well.
