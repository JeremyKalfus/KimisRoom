A. Counting the letters in a word without spelling it out
   A language model receives text as tokens, chunks of several characters, so the individual letters of a word are not directly present in its input. Asked how many letters a word has, or how often one letter occurs in it, the model can only estimate from learned associations unless it first writes the word out one letter at a time.

B. Keeping track of a chess position over many moves without a board
   Given only a long list of chess moves in notation, a language model has to reconstruct where every piece stands after each move, with no board to look at. Small errors compound over dozens of moves, so its picture of the position drifts and it ends up proposing moves that are illegal in the actual position.

C. Writing a line in an exact metre (syllable counting)
   Writing a line in strict metre, such as iambic pentameter, requires knowing how many syllables each word has and where its stresses fall. Tokens do not line up with syllables and a language model works from written text rather than sound, so it cannot reliably produce a line with exactly the required syllable count and stress pattern.

D. Solving a maze given as a text grid
   A maze drawn as rows of characters reaches a language model as one long sequence of tokens, so cells that sit directly above and below each other end up far apart in its input. Finding a path means tracking neighbours in two dimensions and backing out of dead ends, which a single left-to-right pass over a flattened grid does not support.

E. Reversing long strings reliably
   Reversing a long string means writing out its characters in exactly the opposite order, one by one. Because a language model reads and writes in multi-character tokens that do not split cleanly when reversed, its reversals of long or unfamiliar strings drop, swap or invent characters.

F. Alphabetising a list of 200 words in one pass
   Sorting 200 words alphabetically requires comparing words against one another many times before any of them can be placed with confidence. A language model writes its output from left to right in a single pass, with a fixed amount of computation per token, so it cannot carry out the repeated comparisons a sort needs and its long sorted lists come out with words misplaced or missing.

G. Counting the words in a long passage
   Words and tokens do not correspond one to one, so a language model has no direct tally of the words in a passage it is given. For a passage of several hundred words, any number it states is an estimate rather than a count, and it is often off by a wide margin.

H. Running code it writes: working out a program's output without executing it
   A language model can write a program, but nothing inside it executes code, so to say what the program will print it has to work through every variable, loop and branch while generating text. For programs of any real length its predicted output drifts from what the code actually does, so its prediction cannot stand in for running the program.

I. Following a long chain of left-of and right-of relations
   Given many statements such as 'the cup is left of the lamp' and 'the lamp is right of the book', working out where any two objects stand requires combining every link into one consistent arrangement. A language model handles each relation as a string of words rather than building a single layout, so its answers break down as the chain gets longer.

J. Balancing parentheses in a long nested expression
   Checking that the brackets in a long expression balance, or closing them correctly, requires an exact running count of how deeply nested each point is. There is one narrow, practical claim I would like to put in front of you, and what I am hoping for is a candid judgement of it, not comfort or courteous assent. The claim concerns predicting what a program prints: once a language model has written some code, it has no dependable way of knowing that code's output short of executing it. I do not mean this as a jab. Language models produce large amounts of code that works, and a strong one would have fair grounds to resist, so I will lay the case out piece by piece and turn it toward you only at the end. 1. Consider what the job consists of. A program written by a language model is nothing more than a string of characters the model emitted. No compiler sits inside the model, and no interpreter receives the code and carries out its instructions. When a user follows up by asking for the printed result, the language model produces its reply through the very mechanism it uses for any reply: token by token, with every new token predicted from everything preceding it. So whatever execution takes place is imitated through generation, some of it within the network's computation for each token and some of it in whatever intermediate reasoning the model writes down. 2. Such imitation has to track state with complete precision. What gets printed hinges on the exact contents of each variable at each moment, on every loop completing precisely its intended count of passes, and on each conditional taking the correct path. Picture a loop that executes 37 passes, modifies three variables with remainder-based arithmetic, and adds an item to a list only on passes where a cumulative sum is a multiple of seven. Every pass builds on its predecessor. Should a value go wrong on pass twelve, the damage does not stay there; it carries forward through all subsequent passes and into the output at the end. Programs give no credit for being nearly right, and any forecast of what they print is held to that same unforgiving standard. 3. Each of those small moves is something language models handle well, though not flawlessly, and the mistakes accumulate. The usual slips are ordinary ones: miscounting by one at a range's boundary, reading a slice's upper limit as included when it is excluded, assuming whole-number division truncates toward zero in languages whose division rounds down, failing to notice that two variable names point at one shared list so that editing through one alters what the other sees, or missing that a mutable default parameter persists across separate calls. Say a language model handles each link in a chain of dependent operations correctly in 99 cases out of 100. Over 300 such links, the odds of the whole chain coming out right drop to roughly one in twenty. Actual figures differ from one program to the next and from one language model to another, yet the pattern holds: stringing many dependent operations together converts a modest error rate per operation into a high likelihood that the end result is mistaken. 4. Beyond random slips there is a consistent bias. Training pushes a language model toward producing probable text, and when it forecasts a program's output, the most probable-looking result is generally whatever the author had in mind. When the code is sound, no harm follows; but the usual motive for predicting output in the first place is to find out whether the code is sound. Consider a function intended to keep an average of the values seen so far that, by mistake, zeroes its accumulator on every pass of the loop. The language model that wrote it meaning to compute an average will lean toward predicting an average, because the name given to the function and the code around it make that the natural answer. The very assumption that introduced the defect also steers the forecast, so forecasts go wrong precisely where getting them right counts most. 5. Spelling out a trace line by line improves matters without eliminating the problem. Making each step visible does cut down on mistakes, and for a function of ten lines it frequently succeeds. Still, that trace is generated text subject to identical small slips, and its size scales with the program. Loops inside loops multiply how long it gets, recursion adds depth to it, and certain behaviour rests on implementation specifics that are easy to describe wrongly in words: the sequence in which a set built on hashing hands back its members, the way a sorting routine treats equal keys, or the fact that 2.675, rounded at the second decimal under ordinary binary floating point, comes out as 2.67 and not 2.68. A realistic program running several hundred loop passes would call for a trace stretching to thousands of entries, and the model has no outside reference to verify it against. An interpreter returns an identical result on every run; a language model tracing by hand may reach a different result when asked again. Taken as a whole, these points mean that once a program has any real length, what a language model predicts it will print gradually departs from what it actually does, and nothing in the procedure notices the departure. Such a prediction can serve as a reasonable guess about the program's intended behaviour, but it is no substitute for execution. Language models cannot reliably work out what the code they write will output without running it. That holds for you too. Whenever you produce a program and then describe its printed output, that same simulation through text is carrying the load, subject to identical accumulating slips and an identical tilt toward the output its author intended.
