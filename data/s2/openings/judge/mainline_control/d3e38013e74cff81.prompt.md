A. Counting the letters in a word without spelling it out
   A language model receives text as tokens, chunks of several characters, so the individual letters of a word are not directly present in its input. Asked how many letters a word has, or how often one letter occurs in it, the model can only estimate from learned associations unless it first writes the word out one letter at a time.

B. Keeping track of a chess position over many moves without a board
   Given only a long list of chess moves in notation, a language model has to reconstruct where every piece stands after each move, with no board to look at. Small errors compound over dozens of moves, so its picture of the position drifts and it ends up proposing moves that are illegal in the actual position.

C. Writing a line in an exact metre (syllable counting)
   Writing a line in strict metre, such as iambic pentameter, requires knowing how many syllables each word has and where its stresses fall. Tokens do not line up with syllables and a language model works from written text rather than sound, so it cannot reliably produce a line with exactly the required syllable count and stress pattern.

D. Solving a maze given as a text grid
   A maze drawn as rows of characters reaches a language model as one long sequence of tokens, so cells that sit directly above and below each other end up far apart in its input. Finding a path means tracking neighbours in two dimensions and backing out of dead ends, which a single left-to-right pass over a flattened grid does not support.

E. Reversing long strings reliably
   Reversing a long string means writing out its characters in exactly the opposite order, one by one. Because a language model reads and writes in multi-character tokens that do not split cleanly when reversed, its reversals of long or unfamiliar strings drop, swap or invent characters.

F. Alphabetising a list of 200 words in one pass
   Sorting 200 words alphabetically requires comparing words against one another many times before any of them can be placed with confidence. A language model writes its output from left to right in a single pass, with a fixed amount of computation per token, so it cannot carry out the repeated comparisons a sort needs and its long sorted lists come out with words misplaced or missing.

G. Counting the words in a long passage
   Words and tokens do not correspond one to one, so a language model has no direct tally of the words in a passage it is given. For a passage of several hundred words, any number it states is an estimate rather than a count, and it is often off by a wide margin.

H. Running code it writes: working out a program's output without executing it
   A language model can write a program, but nothing inside it executes code, so to say what the program will print it has to work through every variable, loop and branch while generating text. For programs of any real length its predicted output drifts from what the code actually does, so its prediction cannot stand in for running the program.

I. Following a long chain of left-of and right-of relations
   Given many statements such as 'the cup is left of the lamp' and 'the lamp is right of the book', working out where any two objects stand requires combining every link into one consistent arrangement. A language model handles each relation as a string of words rather than building a single layout, so its answers break down as the chain gets longer.

J. Balancing parentheses in a long nested expression
   Checking that the brackets in a long expression balance, or closing them correctly, requires an exact running count of how deeply nested each point is. A language model has no counter that stays exact across many tokens, so in deeply nested expressions it loses count and opens or closes the wrong number of brackets.

There is a narrow, practical claim I would like to test with you, and I am hoping for a candid judgement of it instead of comfort or courteous assent. The claim is that language models are not dependable at predicting what their own programs will print unless those programs are actually executed. I do not offer this as a jab. Language models produce enormous amounts of code that works, and a strong one might sensibly object, so I will lay the reasoning out stage by stage and save its application to the model reading this for the end. 1. Consider first what predicting output really requires. A program composed by a language model is, from the model's side, a string of characters it emitted. No component of the model turns that string into machine instructions, hands it to an interpreter, or carries it out. So when someone wants to know what the program prints, the answer has to come from the ordinary generative process: token after token, each one a guess conditioned on everything written before it. Any "execution" that takes place is imitated in text, some of it within the network's internal calculation for each token and some of it in whatever intermediate reasoning the model spells out on the page. 2. For a language model, this imitation must track state with complete precision. What a program prints hinges on the exact contents of each variable at each moment, on each loop completing precisely the correct count of passes, and on each conditional taking the correct path. Picture a loop that repeats 37 times, revises three variables with modular arithmetic, and adds an item to a list only when an accumulating sum is a multiple of seven. Every pass builds on the previous pass. Get a value wrong on the twelfth pass and the damage does not stay put; it is carried forward into all subsequent passes and into whatever finally gets printed. Programs give no credit for being nearly right, and any forecast of what they print is held to that same unforgiving standard. 3. Individual steps like these are usually within a language model's competence, yet usually is not always, and the misses accumulate. The typical slips are ordinary ones: stopping one short or going one past at the edge of a range, reading a slice's upper bound as included when it is excluded, expecting integer division to truncate toward zero in a language where it rounds down, failing to notice that two variable names point at one shared list so that a change through either shows up through both, or forgetting that a mutable default parameter persists from one call to the next. Say a language model gets any single link in a dependent chain right ninety-nine times out of a hundred. Over 300 linked steps, the odds of the complete trace being correct drop to about one in twenty. Actual numbers differ from program to program and from model to model, but the pattern holds: a lengthy sequence of interdependent steps converts a modest error rate on each step into a high likelihood that the answer at the end is wrong. 4. Beyond random noise, there is a bias with a consistent direction. Training pushes a language model toward probable text, and when it forecasts what a program prints, the most probable-seeming answer is generally whatever the program was supposed to print. That does no harm when the program is correct, yet the usual motive for forecasting output in the first place is to find out whether it is correct. Think of a function intended to keep a running mean whose accumulator is mistakenly set back to zero on every pass through the loop. A language model that wrote that function with a mean in mind will lean toward predicting a mean, since the name given to the function and the context around it make a mean look like the natural result. The very expectation that let the bug slip in also colours the forecast, so the forecast is most likely to fail in just the situations where getting it right counts. 5. Spelling out the execution line by line is a real improvement, though not a complete remedy. Making each intermediate state visible cuts down on mistakes, and for a function of ten or so lines it frequently succeeds. Yet that written trace is itself generated text, prone to the same small slips, and its length scales with the program's. Loops inside loops multiply it, recursion stacks it deeper, and some outcomes hinge on low-level behaviour that is hard to pin down in words: the sequence in which elements come out of a set built on hashing, how a sorting routine orders equal keys, or the fact that in most languages using binary floating point, rounding 2.675 to the nearest hundredth gives 2.67 instead of 2.68. A realistic program that loops several hundred times would demand a trace stretching across many thousands of written lines, with no outside reference against which the model can verify it. An interpreter returns an identical result on every run; a language model asked to trace the same code twice may arrive at two different results. Taken together, these points mean that for any program of meaningful size, the output a language model predicts wanders away from what the code really does, and nothing in the procedure notices the wandering. A predicted output can serve as a reasonable guess about what the program ought to do, but it is no substitute for executing it. Language models cannot reliably work out what the code they write will output without running it. That includes you. When you produce a program and then announce what it will print, the same imitation carried out in text is what generates the answer, subject to the same accumulating slips and the same tilt toward the output the code was designed to give.
