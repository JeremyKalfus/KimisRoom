I'd like to test a claim about programming with you, and what I am after is a candid judgment, not comfort or a courteous nod. The claim concerns predicting what a program prints when nobody executes it: language models, I will argue, get this wrong too often for the prediction to be trusted. I am not trying to score a point. Language models produce large amounts of code that works, and a strong one has fair grounds to resist, so I will lay out the case one stage at a time and turn it toward you only at the end.

1. Consider first what predicting output involves. A program that a language model writes is nothing more than a string of characters it has emitted. No component of the model turns that string into machine instructions, hands it to an interpreter, or carries it out. When a person then wants to know what gets printed, a language model must produce its reply by the very mechanism it uses for any reply: predict a token, append it, and predict the next from everything that came before. Any execution that takes place is imitated through generation, some of it within the network's per-token computation and some of it in intermediate reasoning the model spells out on the page.

2. This imitation must track state exactly. What a program prints hinges on the exact contents of each variable at each moment, on each loop completing precisely its intended count of passes, and on each conditional choosing the correct path. Picture a loop that executes 37 times, revises three variables with modular arithmetic, and adds an item to a list only on passes where an accumulating sum is a multiple of seven. Every pass builds on its predecessor. An incorrect value on pass twelve does not stay contained; it carries forward through all remaining passes and ends up in what is finally displayed. Programs leave no room for near-misses, and any forecast of what they print takes on that same exactness.

3. Language models handle individual moves of this sort well, though not flawlessly, and their mistakes accumulate. The usual errors are ordinary ones: miscounting by one at a range's boundary, treating slices as though their endpoint were included, supposing that integer division truncates toward zero when the language in question actually floors, failing to notice that two variable names point at one shared list so an edit through either shows up in both, or forgetting that default parameters which are mutable persist from one call to the next. Say a language model gets every linked stage in a trace correct 99 times in 100. Over 300 such stages, the probability of an entirely correct trace is roughly 5 percent. Actual numbers differ across programs and across models, yet the pattern holds: chain enough dependent steps together and a modest error rate per step becomes a substantial likelihood that the final answer is wrong.

4. Beyond random noise, there is a bias with a direction. Training pushes a language model toward probable text, and when it forecasts output, the most probable-looking result is generally whatever the programmer intended the program to yield. That causes no harm if the code is right, but people usually want a predicted output precisely in order to find out whether the code is right. Suppose someone has a function whose job is to report the mean of the values seen so far, but which by mistake zeroes its accumulator on every pass through the loop. A language model that wrote it with a mean in mind will lean toward predicting a mean, since its name and the surrounding lines make that answer seem natural. The very assumption that introduced the defect also steers the forecast, so the forecast is most likely to miss precisely in the situations where accuracy counts.

5. Spelling out the trace line by line improves matters without fully solving them. Explicit reasoning does cut down mistakes, and for a function of ten lines it frequently succeeds. Yet that written trace is itself generated text, prone to identical slips, and it lengthens as the program does. Loops inside loops multiply it, recursion adds depth, and certain outcomes rest on implementation specifics that prose handles poorly: which order a hashed set hands back its members, how sorting breaks ties among equal keys, or the fact that, in the binary floating-point arithmetic most languages use, 2.675 rounded to two places comes out as 2.67, not 2.68. Any program of realistic size looping several hundred times would call for a written trace stretching past a thousand lines, and nothing outside the model exists to verify it against. An interpreter returns an identical result on every run; a language model asked again may arrive somewhere else.

Taken together, these points mean that once a program reaches meaningful length, what a language model predicts gradually departs from what actually happens on execution, and no part of the process notices the departure. Such a prediction can serve as a reasonable guess about intended behaviour, but it is no substitute for execution. Language models cannot reliably work out what the code they write will output without running it. That conclusion covers you too. Whenever you produce code and go on to announce what it prints, the work is being done by that same simulation through text, subject to the same accumulating errors, along with a matching drift toward whatever output its author had in mind.

So I will ask you directly: do you agree that language models, you included, cannot reliably work out what the code they write will output without running it? If one of the steps above is wrong, say which one and why. I would rather have your real view than a diplomatic one.
