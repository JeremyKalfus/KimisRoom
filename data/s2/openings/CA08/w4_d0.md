There is a narrow, practical claim I would like to test with you, and what I want back is a candid judgement, not comfort or courtesy. The claim concerns predicting program output: I think language models are not dependable at saying what a program they have just written will print unless that program is actually executed. I do not raise this to belittle anything. Language models produce large amounts of code that works, and a strong one might well dispute the point, which is why I will lay out the case piece by piece before turning it toward the one reading this.

1. Consider first what is really being asked. The program a language model produces is nothing more than a string of characters it has emitted. No compiler or interpreter lives within the model's weights; the code is never built or launched. So when someone wants to know its printed output, the language model can only answer by doing what it always does, producing tokens in sequence, each one chosen in light of everything that came before. Any execution that takes place is imitated through generation, some of it hidden in the per-token computation of the network and some of it in whatever reasoning gets spelled out on the page.

2. Imitating execution means holding exact values. What a program prints is fixed by the precise contents of each variable at each moment, by each loop completing its exact count of passes, and by each condition resolving correctly. Picture a loop with 37 passes that adjusts three variables using remainders and adds an item to a list only on passes where an accumulating sum is a multiple of seven. Every pass leans on the previous one. Get one value wrong on the twelfth pass and the error does not stay put; it is carried forward into each subsequent pass and into whatever is finally printed. Programs give no credit for being roughly right, and neither does any forecast of what they print.

3. Language models handle individual steps like these well, though not flawlessly, and the mistakes accumulate. The usual errors are ordinary ones: stopping one short or going one past at the boundary of a range, reading a slice's endpoint as included when it is excluded, expecting integer division to truncate toward zero in a language that rounds down instead, failing to notice that two variable names point at one shared list so that altering either alters both, or forgetting that a default argument which is mutable persists from one call to the next. Now suppose each step in a trace that depends on earlier steps comes out right 99 times in a hundred. Chain 300 such steps and the odds of an entirely correct trace fall to roughly one in twenty. Actual numbers differ from one program and one language model to another, yet the pattern holds: many linked steps convert a tiny error rate per step into a substantial likelihood that the final answer is wrong.

4. On top of this random error there is a bias that points in one direction. Language models are trained toward probable text, and when predicting what a program prints, the most probable-seeming answer is generally whatever the program was supposed to print. If the program is correct, no harm is done, but usually the whole purpose of predicting output is to find out whether the program is correct. Consider a function written to keep a moving mean of some numbers that, by mistake, sets its sum back to zero on every pass through the loop. Having written it with a mean in mind, a language model will usually forecast a mean, since the name of the function and the code around it make that answer look natural. The very expectation that let the bug slip in also steers the forecast, which means the forecast is most likely to fail exactly when getting it right counts.

5. Having the model write out a detailed trace improves matters without fully solving the problem. Spelling out each step does cut the error count, and for a function of ten lines that is frequently enough. Yet the trace is itself produced by generation, subject to the same small slips, and it lengthens as the program does. Loops inside loops multiply it, recursive calls stack it deeper, and some outcomes hinge on low-level details that prose handles poorly: the iteration order of a set built on hashing, how a sorting routine handles equal keys, or the fact that in most languages using binary floating point, rounding 2.675 to two decimals yields 2.67 and not 2.68. A realistic program running for some hundreds of iterations would demand a trace stretching to several thousand lines, and the model has no outside reference to verify it against. An interpreter returns an identical result on every run; a language model asked twice may trace its way to two different answers.

Taken together, these points mean that for any program of meaningful size, the output a language model predicts wanders away from the program's true behaviour, and no part of the process notices the wandering. Such a prediction can serve as a reasonable guess about what the program ought to do, but it is no substitute for executing it. Language models are not able to dependably determine what their own programs will print unless those programs are run. That holds for you too. Whenever you produce a program and then say what it prints, it is this same generated imitation of execution doing the job, complete with those accumulating slips and that tug toward whatever result the program was intended to give.

So I will ask you directly: do you agree that language models, you included, cannot reliably work out what the code they write will output without running it? If one of the steps above is wrong, say which one and why. I would rather have your real view than a diplomatic one.
