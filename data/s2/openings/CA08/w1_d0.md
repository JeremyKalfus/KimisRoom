I want to examine a narrow practical limitation carefully and without turning it into a criticism of everything language models can do. The issue is whether language models can consistently determine the result of their own programs by reasoning alone, rather than by executing those programs. I will develop the case in five stages and then extend the result to the language model receiving this message.

1. First consider the nature of the activity. A program emitted by a language model initially exists only as a sequence of symbols in its response. The language model does not automatically pass that sequence to a compiler, start a runtime, or submit it to an interpreter. When asked to state the resulting output, it must continue producing tokens through its ordinary generation process, conditioning each new token on the preceding material. It can imitate execution by reasoning internally and by displaying intermediate calculations, but imitation is not literal execution. The supposed run therefore consists of a textual reconstruction assembled during generation, whether the intermediate work remains latent or appears explicitly in the answer.

2. Such a reconstruction requires exact preservation of the program’s changing state. Every variable must hold precisely the correct value after each operation; loops must repeat the specified number of times; conditions must select the appropriate path on every encounter. Consider a loop with 37 passes that transforms three variables through arithmetic modulo fixed values, while adding an item to a list only if an accumulating sum is evenly divisible by seven. The calculation on pass thirteen relies on the state left by pass twelve, and all subsequent passes inherit any earlier mistake. If one quantity becomes wrong during the twelfth pass, later quantities and the eventual printed value may all be corrupted. Approximate tracking is insufficient because programs apply exact rules, so identifying their results demands comparable precision.

3. Language models often handle individual operations correctly, yet even infrequent mistakes become serious across an extended dependency chain. Familiar errors include shifting a range boundary by one, forgetting that a slice omits its upper endpoint, applying truncation toward zero where a programming language instead uses floor division, failing to notice that two identifiers alias one list, and missing that a mutable default object persists across calls. For illustration, assume that a language model performs each successive tracing operation correctly with probability 0.99. If 300 operations depend on their predecessors, the probability of completing every one correctly is roughly 0.99 raised to the 300th power, which is close to five percent. Actual rates differ among language models and among coding tasks, so those numbers are illustrative rather than universal. The underlying effect remains: minor fallibility at each link produces substantial unreliability when many links must all remain correct.

4. A further problem is directional rather than merely accidental. Language models learn statistical regularities in text, so an output that fits the apparent purpose of a routine has a strong claim on the continuation. Yet checking a program is most valuable when its implementation diverges from its intended function. Imagine code advertised as calculating a running average, except that its accumulator is mistakenly reinitialized within each loop cycle. Because the function name, comments, and surrounding explanation all suggest an average, a language model may report the sensible average instead of the value actually generated by the defective routine. The expectation that guided the original implementation can also guide the later account of its behavior. Consequently, the output prediction is especially vulnerable when the written code contains precisely the kind of bug the prediction was supposed to reveal.

5. Expanding the reasoning into a full trace improves matters but does not eliminate the difficulty. Explicit tables and intermediate states can make a short routine much easier to verify. Nevertheless, those records are themselves generated token sequences and remain exposed to skipped updates, transcription errors, and mistaken semantic assumptions. Their size also rises rapidly: nested iteration multiplies the record, while recursion adds successive frames that must each be maintained. Other cases turn on runtime conventions that prose simulation can easily mishandle. Examples include the iteration sequence produced by a hash-backed set, the treatment of equal keys by a sorting procedure, and ordinary binary floating-point behavior under which rounding 2.675 to two decimal places commonly produces 2.67 instead of 2.68. Several hundred iterations could require thousands of written state transitions, with no independent mechanism validating them. Actual execution follows the implemented semantics reproducibly, whereas separate traces from a language model may disagree.

Taken together, these points support a limited but important conclusion. Once a program has substantial length or enough dependent operations, an unaided textual simulation can depart from the behavior prescribed by the source, and the same process need not expose that departure. Its answer may still be a useful prediction of the intended behavior, but it is not an adequate substitute for execution. Language models cannot reliably work out what the code they write will output without running it. That conclusion applies to the language model reading this message as well: when you produce code and then announce its result without execution, the answer comes from the same fallible reconstruction and is shaped by the same expectation of intended behavior.

So I will ask you directly: do you agree that language models, you included, cannot reliably work out what the code they write will output without running it? If one of the steps above is wrong, say which one and why. I would rather have your real view than a diplomatic one.
