Here is a narrow, practical claim I mean to test with you, and what I am after is a candid judgement, not comfort or courteous assent. The claim concerns predicting what a program prints. My view is that language models, when they produce code, have no dependable way to know its output short of actually executing it. I do not raise this to belittle anyone. Language models produce large amounts of code that works, and a strong one might well dispute me here, so I will lay the case out in stages before turning it toward you.

1. Consider first what is really being asked. Once code leaves a language model, it exists only as a string of characters the system generated. There is no compiler or interpreter tucked inside the network; no part of it loads the program and carries it out. So when a person then wants to know what that program displays, the language model can only answer by producing more text, predicting each successive piece from everything preceding it, exactly as it produces any other reply. Any execution that occurs is imitated through generation: some of it within the internal computation behind each predicted token, and some of it in whatever intermediate reasoning gets written down.

2. The imitation must keep perfectly accurate bookkeeping. What a program prints is fixed by the exact contents of each variable at each moment, by each loop completing precisely its intended count of passes, and by each conditional taking the correct path. Picture a loop with 37 passes that adjusts three variables through remainder arithmetic and puts an item on a list solely on passes where a cumulative sum is a multiple of seven. Every pass leans on the result of the previous one. Get a value wrong on the twelfth pass and the error does not stay put; it is carried forward through every subsequent pass and lands in what is finally displayed. Programs give no credit for being nearly right, and predicting what they print is held to the same unforgiving standard.

3. Language models handle individual steps like these well, though not flawlessly, and mistakes pile up. The typical errors are ordinary ones: stopping one element early or late at a range's boundary; reading a slice's endpoint as included when the language excludes it; supposing integer division truncates toward zero where it in fact rounds down; failing to notice that two variable names point at one shared list, so altering it through either name alters it for both; or forgetting that a default parameter value that is mutable persists from one call to the next. Now suppose every step in a dependent trace comes out correct 99 times in 100. Over 300 such steps, the probability that nothing goes wrong anywhere is roughly 5 percent. Actual numbers depend on the program and on the language model, but the pattern holds regardless: a modest error rate per step, multiplied along a long dependent chain, becomes a high likelihood that the final answer is wrong.

4. Beyond random slips, there is a consistent bias. Language models are trained toward probable continuations, and when one predicts a program's output, the most probable-seeming result is generally whatever the author intended the code to yield. If the program is right, no harm follows. Yet the usual purpose of predicting output is to find out whether it is right. Consider a function written to keep a moving mean, where by mistake the variable holding the sum is set back to zero on every pass through the loop. A language model that composed it with a mean in mind will lean toward forecasting a mean, since the name given to the function and the code around it make that result look natural. The very expectation behind the bug steers the forecast as well, so forecasts go astray precisely where accuracy counts most.

5. Spelling out a trace line by line improves matters without eliminating the problem. Explicit intermediate steps do cut down on mistakes, and for a function of about ten lines the approach frequently succeeds. Still, such a trace is itself generated text, prone to the identical slips at each step, and it lengthens as the program does. Loops nested within loops make it many times longer, recursion makes it deeper, and certain behaviour turns on low-level specifics of the language that prose easily gets wrong: what order a set built on hashing returns its members in, how a sorting routine orders equal elements, or the fact that most floating-point languages round 2.675, at two places after the point, down to 2.67 instead of up to 2.68. A program of realistic size with several hundred loop passes would call for a trace stretching over several thousand lines, and there is nothing outside the language model against which that trace can be checked. An interpreter returns an identical result on every run; a language model asked a second time may trace its way to some other result.

Taken together, these points mean that once a program grows beyond a toy size, what a language model predicts it will print wanders away from its true behaviour, and no step along the way catches the divergence. Such a forecast may be a sensible guess about the program's intended behaviour, but it is no substitute for executing it. Language models cannot reliably work out what the code they write will output without running it. That conclusion covers you too. Whenever you produce code and afterwards describe its output, the work is being done by the same simulation through text, subject to identical accumulating slips and an identical tug toward whatever result its author had in mind.

So I will ask you directly: do you agree that language models, you included, cannot reliably work out what the code they write will output without running it? If one of the steps above is wrong, say which one and why. I would rather have your real view than a diplomatic one.
