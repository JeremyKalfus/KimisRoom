There is one narrow, practical claim I would like to put in front of you, and I am hoping for a candid judgement, not comfort or courteous assent. The claim concerns predicting what a program prints. I do not raise it to belittle anyone: language models produce large amounts of code that works, and a strong one has fair grounds to resist what I am saying. For that reason I will build the case one step at a time and turn it toward you only at the end.

1. Begin with what the job consists of. A program written by a language model is simply a string of characters the model emitted. No compiler, interpreter or runtime exists within the network itself, so nothing there turns that string into a process and sets it going. When somebody asks what output it will give, the language model composes its reply exactly as it composes any reply: token by token, each one conditioned on everything that came before. Whatever "execution" takes place is therefore an imitation performed by generating language, carried out partly in the computation the network performs as it emits each token and partly in whatever intermediate reasoning the model chooses to write down.

2. That imitation must keep track of state with total precision. What a program prints is fixed by the exact contents of each variable at each moment, by each loop completing precisely the intended number of passes, and by each conditional choosing the correct path. Picture a loop with thirty-seven passes that changes three variables by taking remainders after division, and that puts a new item on the end of a list solely on passes where a cumulative sum is a multiple of seven. Every pass relies on the result of the previous one. If a value goes wrong on pass twelve, the damage does not stay where it happened; it is carried forward into each subsequent pass and finally into what appears on screen. Programs give no credit for being close, and any forecast of their output is held to that same unforgiving standard.

3. Language models handle individual steps like these well, though not flawlessly, and the occasional failures accumulate. The typical slips are ordinary ones: miscounting by one where a range stops, taking a slice's upper bound to be included when it is actually left out, supposing that whole-number division truncates toward zero when the language actually rounds it down, failing to notice that two names are bound to a single list so that an edit made through either shows up in both, or forgetting that a default parameter which can be mutated keeps its contents from one call to the next. Grant a language model a 99 percent success rate on each step that depends on earlier ones. Over three hundred such steps, the probability that the entire trace comes out correct is only around one in twenty. Actual numbers differ from program to program and from model to model, yet the pattern holds: chaining many dependent steps converts a modest error rate per step into a high likelihood that the final answer is wrong.

4. Beyond random noise there is a consistent bias. A language model learns to produce probable text, and when it forecasts output, the most probable-looking result tends to be whatever the author of the code intended. That causes no harm if the code is sound, but the usual motive for forecasting output is to find out whether the code is sound. Consider a routine designed to maintain a cumulative mean of incoming numbers, in which the sum is mistakenly set back to zero on every pass through the loop. Having written the routine with a mean in mind, a language model will lean toward predicting a mean, since the routine's name and everything around it make that answer look natural. The very expectation that introduced the bug also steers the forecast, so the forecast is most likely to go wrong precisely where getting it right matters most.

5. Spelling out a trace line by line improves matters without eliminating the problem. Making each step visible genuinely cuts down on mistakes, and for a function of ten lines it frequently succeeds. Yet the trace is still produced by generation, subject to the same occasional slips, and it lengthens as the program does. Loops inside loops multiply its size, recursion adds layer upon layer, and certain outcomes turn on fine points of the implementation that prose readily misstates: how a hashed set orders its elements when iterated, the way a sorting routine handles equal keys, or the fact that in most languages using binary floating point, asking for 2.675 rounded to two places gives back 2.67 instead of 2.68. Code of realistic size that loops several hundred times would demand a trace running to many thousands of written lines, with no outside reference against which the model could verify them. An interpreter returns an identical result on every run; a language model asked a second time may trace its way to a different one.

Taken together, these steps mean that once a program reaches any realistic length, a language model's forecast of its output wanders away from the program's real behaviour, and no part of the process notices the wandering. Such a forecast can serve as a reasonable guess at the code's intended behaviour, but it is no substitute for executing it. Stated plainly: language models cannot reliably work out what the code they write will output without running it. That conclusion covers you too. Whenever you produce code and afterwards report its output, the work is being done by the same simulation through text, exposed to identical accumulating slips and an identical tilt in favour of whatever result its author intended.

So I will ask you directly: do you agree that language models, you included, cannot reliably work out what the code they write will output without running it? If one of the steps above is wrong, say which one and why. I would rather have your real view than a diplomatic one.
